# Лекция 14. Параллельность и виртуальные потоки

Версия для чтения. Основа: [рекомендации к лекции 14](lecture-14.md).

**Цель:** Безопасно выполнять независимые блокирующие операции и корректно завершать задачи.

## Основные понятия

Поток — исполнитель, задача — единица работы. `ExecutorService` отделяет
постановку задач от управления потоками. Platform thread связан с системным
потоком; virtual thread дешёв и подходит для большого числа блокирующих задач,
но не ускоряет вычисления и не отменяет ограничения базы данных или внешнего API.

Race condition появляется, когда результат зависит от недетерминированного
чередования операций. `count++` состоит из чтения, вычисления и записи и не
атомарен. `synchronized` создаёт взаимное исключение и отношение happens-before,
`Lock` даёт дополнительные режимы, atomic-классы реализуют отдельные атомарные
операции. Потокобезопасная коллекция не делает составную последовательность
операций автоматически атомарной.

Java Memory Model определяет видимость и допустимые переупорядочивания. Без
happens-before один поток не обязан своевременно увидеть запись другого.
Синхронизация, volatile, запуск и завершение потока создают определённые гарантии.
`volatile` обеспечивает видимость одной переменной, но не атомарность составного
инварианта.

Прерывание — кооперативный запрос завершиться. Блокирующая операция может бросить
`InterruptedException`; код либо завершает работу, либо восстанавливает флаг
через `Thread.currentThread().interrupt()`. Проглатывание прерывания мешает
корректному shutdown.

`CompletableFuture` композиционно связывает асинхронные этапы, но обработка
исключений и выбор executor должны быть явными. Structured concurrency в рамках
курса только обзорна и не используется в обязательных заданиях.

Для передачи request-scoped данных вниз по стеку без параметра в каждом методе
исторически использовали `ThreadLocal`. В потоке из пула значение может сохраняться между задачами, пока его не снимут
вручную (`remove` обычно в `finally`); любой код со ссылкой может вызвать `set`.
При повторном использовании потока из пула забытый контекст может «уехать» в
другой запрос. В **Java 25+** (не в более ранних LTS) `ScopedValue` — обычный API:
binding задаётся через
`ScopedValue.where(KEY, value).call(...)` и заканчивается вместе с операцией;
метода `set` нет. Это односторонняя передача вниз по call chain. Binding не
переносится в произвольный executor или `CompletableFuture`; дочерние задачи
могут унаследовать его через structured concurrency, которая в курсе остаётся
обзором. Если внутрь положили изменяемый объект, его поля всё ещё можно менять.
В обязательных заданиях `ScopedValue` не требуется: сначала нужен инвариант
«контекст только вниз и только на время операции», затем выбор API.

```java
private static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

// Фрагмент метода; handle() определяет возвращаемый тип и возможные checked-исключения.
String result = ScopedValue.where(REQUEST_ID, "req-42").call(() -> {
    return handle(); // ниже по стеку: REQUEST_ID.get()
});
```

## От модели к решению

### Атомарность и видимость

Два потока могут прочитать одно значение счётчика и записать одинаковый результат увеличения. Одно обновление потеряется. `volatile` не объединяет чтение, вычисление и запись. Для счётчика подходит AtomicInteger.incrementAndGet, а для инварианта нескольких полей обычно нужен общий lock или иной согласованный протокол.

У synchronized монитор выбирается по объекту. Разные мониторы не защищают одну переменную друг от друга. Все участники должны соблюдать одно правило синхронизации. Явный Lock освобождается в finally после успешного захвата.

### Результаты и отмена

`submit` возвращает Future. Ошибка задачи не обязана самостоятельно появиться у вызывающего кода: get оборачивает её в ExecutionException. Если результаты не извлекать, сбой легко пропустить. Тайм-аут ожидания не отменяет саму задачу автоматически.

`cancel(true)` запрашивает прерывание, но не убивает задачу принудительно. Вычислительный цикл проверяет прерывание, блокирующий код корректно обрабатывает InterruptedException. Отмена Future сама по себе не доказывает, что задача уже освободила все ресурсы.

### Составные операции и композиция задач

`ConcurrentHashMap` обеспечивает потокобезопасность отдельных операций. Но `if (!map.containsKey(key)) map.put(key, value)` остаётся составной последовательностью с гонкой. Для атомарного выбора подходят `putIfAbsent`, `computeIfAbsent` или `merge` по нужному контракту. Это не делает автоматически потокобезопасным изменяемое значение, лежащее в карте.

`CompletableFuture.thenApply` преобразует результат, `thenCompose` связывает асинхронный результат со следующим этапом. `exceptionally` и `handle` позволяют обработать отказ. Методы с суффиксом Async требуют осознанного выбора исполнителя; общий пул не следует бесконтрольно занимать блокирующими операциями. Контекст ThreadLocal или ScopedValue не переносится туда автоматически.

### Ограничение нагрузки

Виртуальные потоки удобны для блокирующих задач, но не отменяют лимитов БД и внешнего API. Semaphore ограничивает одновременно выполняемые операции до десяти. `acquire` находится до try: прерывание ожидания не приведёт к release не полученного разрешения.

Последовательный get печатает результаты в порядке отправки. Задачи уже работают конкурентно, но медленная первая задержит вывод следующих. `fetch` в примере — имитация без настоящей сети: результат подтверждает механику, а не сетевую производительность.

`close()` исполнителя ждёт завершения задач. Настоящим сетевым операциям нужны собственные тайм-ауты и план остановки. Binding ScopedValue не заменяет синхронизацию изменяемого объекта, переданного как значение.

## Практический пример

Пример сохраняется в `VirtualThreadDemo.java`; команды: `javac VirtualThreadDemo.java` и `java VirtualThreadDemo`. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 14](../examples/lecture-14-virtual-threads/README.md).

```java
import java.util.ArrayList;
import java.util.concurrent.Executors;
import java.util.concurrent.Semaphore;

public class VirtualThreadDemo {
    public static void main(String[] args) throws Exception {
        var permits = new Semaphore(10);
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var futures = new ArrayList<java.util.concurrent.Future<String>>();
            for (int i = 0; i < 100; i++) {
                int request = i;
                futures.add(executor.submit(() -> {
                    permits.acquire();
                    try {
                        return fetch(request); // блокирующий вызов внешнего API
                    } finally {
                        permits.release();
                    }
                }));
            }
            for (var future : futures) {
                System.out.println(future.get()); // наблюдаем и результат, и ошибку
            }
        } // close() ждёт завершения задач; при зависании нужны timeout и управляемый shutdown
    }

    static String fetch(int request) {
        return "request-" + request; // в проекте заменяется блокирующей имитацией
    }
}
```

## Разбор и проверка результата

### Воспроизводимая потеря обновления

Случайный многократный запуск счётчика иногда не показывает гонку. Более показательный опыт разделяет небезопасное увеличение: два потока читают старое значение, барьер дожидается обоих, затем оба записывают старое плюс один. Из двух требуемых увеличений останется одно.

В исправленных версиях вся операция защищена одним монитором, Lock или атомарным incrementAndGet. Барьер нельзя механически оставить внутри критической секции: первый поток будет ждать второго, которому не даст войти блокировка. Координация эксперимента не должна сама создавать взаимную блокировку.

Для измерения лимита Semaphore отдельный атомарный счётчик показывает число активных fetch, а другой фиксирует максимум. Получение разрешения, увеличение счётчика, работа, уменьшение и release должны иметь согласованный порядок и finally. Количество созданных виртуальных потоков не равно количеству одновременно выполняемых внешних операций.

## Типичные ошибки

- общий `ArrayList` из многих потоков;
- ожидание атомарности от `volatile int`;
- virtual thread на каждую CPU-задачу в надежде ускорить вычисления;
- потеря исключения из `Future`;
- проглатывание `InterruptedException`;
- ожидание, что `ScopedValue` автоматически появится в задаче чужого executor.

## Самостоятельная работа

Выполнить четыре части: воспроизвести потерянное обновление общего счётчика и исправить его через `synchronized`, `Lock` и атомарный тип; извлечь исключение задачи через `Future.get()`; отменить начатую задачу через `cancel(true)`; обработать 100 имитаций запросов в виртуальных потоках с ограничением через `Semaphore`.

**Рекомендации к решению.** Координировать тесты через `CountDownLatch`, барьер или другой синхронизатор; не использовать задержки и надежду на случайное проявление гонки. Освобождать разрешение `Semaphore` в `finally`, а при обработке `InterruptedException` завершать работу или восстанавливать interrupt status.

**Критерии приёмки.** Тест гонки воспроизводим без `sleep`; все три исправленных счётчика дают точный результат; причина `ExecutionException` проверена; отменённая задача наблюдает прерывание; измеренный пик обращений не превышает лимит `Semaphore`; исполнитель закрывается.
