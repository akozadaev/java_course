# Лекция 16. Работа с базами данных в Java: JDBC, транзакции и миграции

## Введение

В предыдущих темах мы рассматривали логику приложения и работу с памятью. Однако данные должны сохраняться надежно, переживать перезапуски приложения и быть доступными для многих пользователей одновременно. Для этого используются реляционные базы данных (РБД).

В этой лекции мы разберем, как Java-приложение взаимодействует с базой данных через стандартный интерфейс **JDBC**, как гарантировать целостность данных с помощью **транзакций** и как безопасно управлять структурой базы данных через **миграции**.

**Цель занятия:** Научиться выполнять параметризованные запросы к БД, правильно управлять границами транзакций и избегать типичных ошибок безопасности и целостности.

## 1. Основы взаимодействия: JDBC

Java Database Connectivity (JDBC) — это API, который позволяет Java-программам выполнять SQL-запросы к любой реляционной базе данных.

### Ключевые компоненты JDBC

1.  **JDBC URL**: Строка подключения, которая говорит драйверу, где находится база данных, какой это тип БД (PostgreSQL, MySQL, H2 и т.д.) и какие параметры соединения использовать.
    *   Пример: `jdbc:postgresql://localhost:5432/mydb`
2.  **Connection**: Объект, представляющий физическое или логическое соединение с базой данных. Это дорогой ресурс, который нельзя создавать для каждого запроса.
3.  **PreparedStatement**: Интерфейс для выполнения параметризованных SQL-запросов. В отличие от обычного `Statement`, он предварительно компилирует запрос и защищает от SQL-инъекций.
4.  **ResultSet**: Таблица данных, возвращаемая базой данных в результате выполнения запроса `SELECT`.

### Почему важен PreparedStatement?

Самая частая ошибка новичков — формирование SQL-запроса через конкатенацию строк:

```java
// ❌ ОПАСНО: Уязвимость к SQL Injection
String sql = "SELECT * FROM users WHERE name = '" + userName + "'";
Statement stmt = connection.createStatement();
ResultSet rs = stmt.executeQuery(sql);
```

Если пользователь введет в поле `userName` значение `' OR '1'='1`, запрос вернет всех пользователей, а при более сложной атаке может удалить данные.

Правильный подход — использование плейсхолдеров (`?`):

```java
// ✅ БЕЗОПАСНО: Параметры передаются отдельно от SQL-кода
String sql = "SELECT * FROM users WHERE name = ?";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, userName); // Данные экранируются автоматически
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            // обработка результата
        }
    }
}
```

> **Важно:** Ресурсы `Connection`, `PreparedStatement` и `ResultSet` необходимо закрывать после использования. В современном Java для этого используется конструкция **try-with-resources**, которая гарантирует закрытие даже при возникновении исключений.

### Пул соединений (Connection Pool)

Создание нового соединения с БД — тяжелая операция (сетевое рукопожатие, аутентификация). В реальных приложениях используют **пул соединений** (например, HikariCP).
*   Приложение не создает `Connection` напрямую, а берет готовое из пула.
*   После использования соединение не закрывается физически, а возвращается в пул для повторного использования.
*   Это значительно повышает производительность под нагрузкой.

## 2. Целостность данных и индексы

База данных отвечает за хранение данных, поэтому она должна защищать их от некорректных состояний, независимо от того, что пишет разработчик в коде приложения.

### Ограничения целостности (Constraints)

*   **Primary Key (PK)**: Уникальный идентификатор строки. Не может быть `NULL`.
*   **Foreign Key (FK)**: Ссылка на первичный ключ другой таблицы. Гарантирует, что вы не сможете создать заказ для несуществующего клиента.
*   **NOT NULL**: Запрещает отсутствие значения в столбце.
*   **UNIQUE**: Гарантирует уникальность значений в столбце (например, email пользователя).
*   **CHECK**: Позволяет задать произвольное условие (например, `price > 0`).

> **Правило:** Проверки в коде приложения (валидация) нужны для удобства пользователя (быстрый отклик), но проверки в БД (constraints) обязательны для защиты данных при конкурентном доступе или сбоях.

### Индексы

Индекс — это дополнительная структура данных, которая ускоряет поиск, сортировку и фильтрацию, но замедляет запись (так как индекс нужно обновлять при каждом `INSERT/UPDATE`).

*   Индексы полезны для столбцов, по которым часто идет поиск (`WHERE id = ...`) или соединение таблиц (`JOIN`).
*   Нельзя индексировать все столбцы «на всякий случай».
*   Для анализа эффективности запроса используйте команду `EXPLAIN` (или `EXPLAIN ANALYZE`), которая показывает план выполнения запроса и указывает, используется ли индекс.

## 3. Транзакции и ACID

Транзакция — это последовательность операций с базой данных, которая выполняется как единое целое. Либо выполняются **все** операции, либо **ни одна**.

### Свойства ACID

1.  **Atomicity (Атомарность)**: Транзакция неделима. Если произошла ошибка посередине, все изменения отменяются (Rollback).
2.  **Consistency (Согласованность)**: Транзакция переводит базу данных из одного корректного состояния в другое, соблюдая все ограничения (FK, CHECK и т.д.).
3.  **Isolation (Изолированность)**: Параллельные транзакции не должны мешать друг другу. Степень изоляции настраивается (Read Committed, Repeatable Read и др.).
4.  **Durability (Долговечность)**: Если транзакция успешно завершена (Commit), данные сохранены даже при отключении питания.

### Управление транзакциями в JDBC

По умолчанию в JDBC включен режим **autocommit**: каждый отдельный SQL-запрос сразу фиксируется в базе. Для группировки операций этот режим нужно отключить.

```java
connection.setAutoCommit(false); // Начало транзакции

try {
    // 1. Создать заголовок заказа
    insertOrderHeader(connection, orderId);
    
    // 2. Добавить позиции заказа
    for (OrderLine line : lines) {
        insertOrderLine(connection, orderId, line);
    }
    
    connection.commit(); // Фиксация: все изменения сохраняются
} catch (SQLException e) {
    connection.rollback(); // Откат: если ошибка, ничего не сохраняется
    throw e;
} finally {
    connection.setAutoCommit(true); // Возвращаем режим по умолчанию
}
```

> **Критическое правило:** Никогда не выполняйте долгие операции (HTTP-запросы, чтение файлов, сложные вычисления) внутри активной транзакции БД. Это держит соединение занятым и блокирует другие транзакции, снижая производительность всей системы. Транзакция должна быть максимально короткой.

## 4. Управление схемой: Миграции Flyway

Изменение структуры базы данных (добавление таблиц, колонок) в процессе разработки и эксплуатации называется миграцией.

**Проблема ручного управления:**
*   Разработчики меняют схему локально.
*   Забывают применить изменения на тестовом сервере.
*   Редактируют уже примененные скрипты, что приводит к рассинхронизации.

**Решение: Flyway**
Flyway — это инструмент версионирования схемы БД.
1.  Миграции хранятся в виде SQL-файлов в репозитории проекта (например, `V1__init.sql`, `V2__add_users_table.sql`).
2.  При запуске приложения Flyway проверяет специальную таблицу в БД (`flyway_schema_history`).
3.  Он применяет только те миграции, которые еще не были выполнены.
4.  **Запрещено редактировать уже примененную миграцию.** Если нужно что-то изменить, создается новая миграция.

Это гарантирует, что база данных на любом окружении (dev, stage, prod) может быть поднята с нуля до актуального состояния одной командой.

## 5. Разбор типовых ошибок

При работе с JDBC и транзакциями чаще всего встречаются следующие ошибки:

| Ошибка | Последствие | Как исправить |
| :--- | :--- | :--- |
| **SQL Injection** | Взлом базы, утечка данных | Использовать `PreparedStatement` с параметрами `?`. |
| **Утечка соединений** | Падение приложения под нагрузкой | Использовать try-with-resources и пул соединений. |
| **Один Connection на всё приложение** | Блокировки, потеря данных в многопоточной среде | Брать соединение из пула на время выполнения метода. |
| **Частичный Commit** | Нарушение целостности (заказ без товаров) | Оборачивать группу операций в одну транзакцию с rollback при ошибке. |
| **Редактирование примененной миграции** | Ошибки при деплое, невозможность воспроизвести состояние | Создавать новые миграции для изменений. Старые не трогать. |

## 6. Практический пример: Поиск товара

Рассмотрим метод поиска названия товара по ID.

```java
static Optional<String> findName(java.sql.Connection c, long id) throws java.sql.SQLException {
    var sql = "select name from product where id = ?";
    // try-with-resources автоматически закроет Statement и ResultSet
    try (var ps = c.prepareStatement(sql)) {
        ps.setLong(1, id);
        try (var rs = ps.executeQuery()) {
            if (rs.next()) {
                return Optional.of(rs.getString("name"));
            } else {
                return Optional.empty();
            }
        }
    }
}
```

**Почему здесь используется `Optional<String>`?**
Возврат `null` является частой причиной `NullPointerException` в вызывающем коде. `Optional` явно сигнализирует вызывающему коду, что результат может отсутствовать, и заставляет обработать этот случай явно.

## 8. Задание для самостоятельной работы

**Тема:** Реализация создания заказа с позициями.

**Требования:**
1.  Создать миграции Flyway для таблиц `orders` (заголовок) и `order_lines` (позиции).
2.  Реализовать сервисный метод, который принимает данные заказа и список позиций.
3.  Метод должен выполняться в одной транзакции:
    *   Вставить запись в `orders`.
    *   Вставить все записи в `order_lines`.
    *   Если любая вставка не удалась — выполнить полный откат (rollback).
4.  Использовать `PreparedStatement` для всех запросов.
5.  Написать интеграционный тест, который проверяет:
    *   Успешное создание заказа.
    *   Отсутствие частичных данных при искусственно вызванной ошибке (например, нарушение ограничения FK или NULL).

**Критерии приемки:**
*   [ ] Повторный запуск миграций не вызывает ошибок.
*   [ ] SQL-инъекция через входные параметры невозможна.
*   [ ] При ошибке добавления второй позиции заказа в базе не остается ни заголовка, ни первой позиции.
