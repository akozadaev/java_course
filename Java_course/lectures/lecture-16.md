# Лекция 16. Работа с базами данных в Java: JDBC, транзакции и миграции

Версия для чтения. Основа: [рекомендации к лекции 16](lecture-16.md).

## Введение

В предыдущих темах мы рассматривали логику приложения и работу с памятью. Однако данные должны сохраняться надежно, переживать перезапуски приложения и быть доступными для многих пользователей одновременно. Для этого используются реляционные базы данных (РБД).

В этой лекции мы разберем, как Java-приложение взаимодействует с базой данных через стандартный интерфейс **JDBC**, как гарантировать целостность данных с помощью **транзакций** и как безопасно управлять структурой базы данных через **миграции**.

**Цель занятия:** Научиться выполнять параметризованные запросы к БД, правильно управлять границами транзакций и избегать типичных ошибок безопасности и целостности.

## 1. Основы взаимодействия: JDBC

Java Database Connectivity (JDBC) — это API, который позволяет Java-программам работать с СУБД, для которой есть совместимый JDBC-драйвер. Драйвер подключается как зависимость; SQL-диалект и возможности базы при этом не становятся одинаковыми.

### Ключевые компоненты JDBC

1.  **JDBC URL**: Строка подключения, которая говорит драйверу, где находится база данных, какой это тип БД (PostgreSQL, MySQL, H2 и т.д.) и какие параметры соединения использовать.
    *   Пример: `jdbc:postgresql://localhost:5432/mydb`
2.  **Connection**: Объект, представляющий физическое или логическое соединение с базой данных. Создание физического соединения обычно затратно. В прикладном коде соединение берут на время операции из пула; простой учебный пример может открывать его напрямую.
3.  **PreparedStatement**: Интерфейс для выполнения параметризованных SQL-запросов. Он отделяет значения параметров от SQL-кода. Подготовка и компиляция на стороне сервера зависят от драйвера и СУБД; автоматическое ускорение не гарантируется.
4.  **ResultSet**: Курсор для чтения результата запроса. Сначала он находится перед первой строкой; вызов `next()` переводит его к следующей строке.

### Почему важен PreparedStatement?

Самая частая ошибка новичков — формирование SQL-запроса через конкатенацию строк:

```java
// ❌ ОПАСНО: Уязвимость к SQL Injection
String sql = "SELECT * FROM users WHERE name = '" + userName + "'";
Statement stmt = connection.createStatement();
ResultSet rs = stmt.executeQuery(sql);
```

Если пользователь введет в поле `userName` значение `' OR '1'='1`, запрос вернет всех пользователей, а другие последствия зависят от прав пользователя БД, драйвера и формы уязвимого запроса.

Правильный подход — использование плейсхолдеров (`?`):

```java
// ✅ БЕЗОПАСНО: Параметры передаются отдельно от SQL-кода
String sql = "SELECT * FROM users WHERE name = ?";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, userName); // Значение связывается с параметром, а не вставляется в SQL
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            // обработка результата
        }
    }
}
```

Плейсхолдеры обозначают значения, а не имена таблиц, столбцов или направление сортировки. Динамическое имя поля выбирают из разрешённого списка. Если непроверенный ввод всё же попадает в SQL через конкатенацию, одного PreparedStatement недостаточно.

> **Важно:** Ресурсы `Connection`, `PreparedStatement` и `ResultSet` необходимо закрывать после использования. В современной Java для этого используется конструкция **try-with-resources**, которая гарантирует закрытие даже при возникновении исключений.

### Пул соединений (Connection Pool)

Создание нового соединения с БД — тяжелая операция (сетевое рукопожатие, аутентификация). В реальных приложениях используют **пул соединений** (например, HikariCP).
*   Приложение не создает `Connection` напрямую, а берет готовое из пула.
*   После использования соединение не закрывается физически, а возвращается в пул для повторного использования.
*   Это значительно повышает производительность под нагрузкой.

## 2. Целостность данных и индексы

База данных отвечает за хранение данных, поэтому она должна защищать их от некорректных состояний, независимо от того, что пишет разработчик в коде приложения.

### Ограничения целостности (Constraints)

*   **Primary Key (PK)**: Уникальный идентификатор строки. Не может быть `NULL`.
*   **Foreign Key (FK)**: Ссылка на подходящий уникальный ключ этой или другой таблицы, часто первичный. Гарантирует, что вы не сможете создать заказ для несуществующего клиента.
*   **NOT NULL**: Запрещает отсутствие значения в столбце.
*   **UNIQUE**: Ограничивает повторы значения или комбинации значений. Правила для NULL зависят от СУБД и настройки ограничения.
*   **CHECK**: Проверяет поддерживаемое СУБД условие строки, например `price > 0`. Обычно результат UNKNOWN из-за NULL не отклоняет строку, поэтому обязательность значения задаётся отдельным NOT NULL.

> **Правило:** Проверки в коде приложения (валидация) нужны для удобства пользователя (быстрый отклик), но проверки в БД (constraints) обязательны для защиты данных при конкурентном доступе или сбоях.

### Индексы

Индекс — это дополнительная структура данных, которая ускоряет поиск, сортировку и фильтрацию, но увеличивает стоимость записей, затрагивающих индексируемые данные, и занимает место.

*   Индексы полезны для столбцов, по которым часто идет поиск (`WHERE id = ...`) или соединение таблиц (`JOIN`).
*   Нельзя индексировать все столбцы «на всякий случай».
*   Для анализа эффективности запроса используйте команду `EXPLAIN` (или `EXPLAIN ANALYZE`), которая показывает план выполнения. EXPLAIN ANALYZE действительно выполняет запрос: для изменяющих запросов это может иметь побочные эффекты.

## 3. Транзакции и ACID

Транзакция — это последовательность операций с базой данных, которая выполняется как единое целое. Либо выполняются **все** операции, либо **ни одна**.

### Свойства ACID

1.  **Atomicity (Атомарность)**: Транзакция неделима. При откате изменения транзакции отменяются. Приложение должно обеспечить rollback при ошибке; внешние HTTP-вызовы и некоторые операции вроде выделения значений sequence не становятся откатываемыми автоматически.
2.  **Consistency (Согласованность)**: Транзакция переводит базу данных из одного корректного состояния в другое, соблюдая все ограничения (FK, CHECK и т.д.).
3.  **Isolation (Изолированность)**: Наблюдаемость промежуточных и конкурентных изменений регулируется уровнем изоляции. Не каждый уровень предотвращает все аномалии; возможны блокировки и необходимость повторить транзакцию. Степень изоляции настраивается (Read Committed, Repeatable Read и др.).
4.  **Durability (Долговечность)**: Если транзакция успешно завершена (Commit), СУБД обеспечивает сохранность в пределах выбранных настроек журналирования, подтверждения записи и гарантий хранилища. Ослабленные настройки могут изменить эту гарантию.

### Управление транзакциями в JDBC

По умолчанию в JDBC включен режим **autocommit**: каждый SQL statement фиксируется как отдельная транзакция после его завершения по правилам JDBC; для результата SELECT момент завершения связан с закрытием результата. Для группировки операций этот режим нужно отключить.

Следующий метод сам получает соединение и владеет всей транзакцией. Он не предназначен для вложенного вызова с уже начатой внешней транзакцией. Методы insertOrderHeader и insertOrderLine — операции предметного проекта, использующие то же соединение; их сигнатуры и SQL определяются схемой.

```java
static void createOrder(javax.sql.DataSource dataSource, long orderId,
                        java.util.List<OrderLine> lines)
        throws java.sql.SQLException {
    try (var connection = dataSource.getConnection()) {
        // Для этой операции ожидается новое, не занятое внешней транзакцией соединение.
        if (!connection.getAutoCommit()) {
            throw new java.sql.SQLException("Expected auto-commit connection");
        }
        connection.setAutoCommit(false);
        try {
            insertOrderHeader(connection, orderId);
            for (OrderLine line : lines) {
                insertOrderLine(connection, orderId, line);
            }
            connection.commit();
        } catch (java.sql.SQLException | RuntimeException | Error failure) {
            try {
                connection.rollback();
            } catch (java.sql.SQLException rollbackFailure) {
                failure.addSuppressed(rollbackFailure);
            }
            throw failure;
        }
    } // close освобождает соединение; у пула обычно возвращает его в пул
}
```

Ошибка rollback не должна скрывать исходную причину. Здесь откатываются также unchecked-ошибки, например сбой проверки позиции после вставки заголовка. Автоматическое закрытие сохраняет ошибку close как suppressed, если основная операция уже завершилась исключением.

После ошибки rollback не следует безусловно вызывать setAutoCommit(true): переключение режима при активной транзакции может её зафиксировать. При работе с пулом нужно использовать его документированный механизм очистки и отбраковки неисправного соединения. Если соединение передаётся извне, владелец внешней транзакции определяет commit, rollback и восстановление состояния.

При сетевом сбое во время commit клиент иногда не знает, была ли транзакция зафиксирована. Слепой повтор создания заказа может создать дубликат: для таких операций нужны устойчивый идентификатор и проверка результата.

> **Критическое правило:** По возможности выносите долгие операции (HTTP-запросы, чтение файлов, сложные вычисления) внутри активной транзакции БД. Это держит соединение занятым и может удерживать блокировки, снижая производительность всей системы. Транзакция должна быть максимально короткой.

## 4. Управление схемой: Миграции Flyway

Изменение структуры базы данных (добавление таблиц, колонок) в процессе разработки и эксплуатации называется миграцией.

**Проблема ручного управления:**
*   Разработчики меняют схему локально.
*   Забывают применить изменения на тестовом сервере.
*   Редактируют уже примененные скрипты, что приводит к рассинхронизации.

**Решение: Flyway**
Flyway — это инструмент версионирования схемы БД.
1.  Миграции хранятся в виде SQL-файлов в репозитории проекта (например, `V1__init.sql`, `V2__add_users_table.sql`).
2.  При выполнении migrate — отдельно или через настроенную интеграцию при запуске приложения — Flyway проверяет специальную таблицу в БД (`flyway_schema_history`).
3.  Он применяет только те миграции, которые еще не были выполнены.
4.  **Запрещено редактировать уже примененную миграцию.** Если нужно что-то изменить, создается новая миграция.

Миграции позволяют воспроизвести схему при совместимых версиях СУБД, наличии прав и необходимых исходных условий. Подъём с нуля и обновление предыдущей версии проверяют отдельно. Атомарность DDL зависит от СУБД: сбой миграции не во всех системах допускает автоматический полный откат.

---

### Пример первой миграции

Для PostgreSQL минимальная схема может выглядеть так. Код сохраняется в `V1__init.sql`; в стандартной интеграции Flyway каталог по умолчанию — `src/main/resources/db/migration`.

```sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    price NUMERIC(12, 2) NOT NULL CHECK (price >= 0)
);
CREATE TABLE orders (
    id BIGINT PRIMARY KEY
);
CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(id),
    product_id BIGINT NOT NULL REFERENCES product(id),
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(12, 2) NOT NULL CHECK (unit_price >= 0)
);
```

Здесь идентификатор заказа назначает приложение; поэтому createOrder принимает orderId. Цена позиции хранится отдельно от текущей цены товара, чтобы изменение каталога не переписывало историю заказа. Валюта и допустимое округление должны быть заданы контрактом приложения. Миграция показывает структуру, но для поиска нужны также тестовые данные.

## 5. Разбор типовых ошибок

При работе с JDBC и транзакциями чаще всего встречаются следующие ошибки:

| Ошибка | Последствие | Как исправить |
| :--- | :--- | :--- |
| **SQL Injection** | Взлом базы, утечка данных | Использовать `PreparedStatement` с параметрами `?`. |
| **Утечка соединений** | Падение приложения под нагрузкой | Использовать try-with-resources и пул соединений. |
| **Один Connection на всё приложение** | Блокировки, потеря данных в многопоточной среде | Брать соединение из пула на время выполнения метода. |
| **Частичный Commit** | Нарушение целостности (заказ без товаров) | Оборачивать группу операций в одну транзакцию с rollback при ошибке. |
| **Редактирование примененной миграции** | Ошибки при деплое, невозможность воспроизвести состояние | Создавать новые миграции для изменений. Старые не трогать. |

## 6. Практический пример: Поиск товара

Рассмотрим метод поиска названия товара по ID. Схема должна задавать `product.name NOT NULL`: пустой Optional означает отсутствие строки, а не SQL NULL. Переданное соединение принадлежит вызывающему коду, поэтому метод его не закрывает.

```java
static java.util.Optional<String> findName(java.sql.Connection c, long id) throws java.sql.SQLException {
    var sql = "select name from product where id = ?";
    // try-with-resources автоматически закроет Statement и ResultSet
    try (var ps = c.prepareStatement(sql)) {
        ps.setLong(1, id);
        try (var rs = ps.executeQuery()) {
            if (rs.next()) {
                return java.util.Optional.of(rs.getString("name"));
            } else {
                return java.util.Optional.empty();
            }
        }
    }
}
```

**Почему здесь используется `Optional<String>`?**
Возврат `null` является частой причиной `NullPointerException` в вызывающем коде. `Optional` явно сигнализирует вызывающему коду, что результат может отсутствовать, и делает этот случай видимым в типе. Вызов get() без проверки всё равно может завершиться исключением; предпочтительны map, orElseGet или orElseThrow.

## 8. Задание для самостоятельной работы

**Тема:** Реализация создания заказа с позициями.

**Требования:**
1.  Создать миграции Flyway для каталога `product`, таблиц `orders` (заголовок) и `order_lines` (позиции).
2.  Реализовать сервисный метод, который принимает данные заказа и список позиций.
3.  Метод должен выполняться в одной транзакции:
    *   Вставить запись в `orders`.
    *   Вставить все записи в `order_lines`.
    *   Если любая вставка не удалась — выполнить полный откат (rollback).
4.  Использовать `PreparedStatement` для всех запросов.
5.  Написать интеграционный тест, который проверяет:
    *   Успешное создание заказа.
    *   Отсутствие частичных данных при искусственно вызванной ошибке (например, нарушение ограничения FK или NULL).

**Критерии приемки:**
*   [ ] Повторный запуск миграций не вызывает ошибок.
*   [ ] Все значения передаются параметрами; динамические идентификаторы SQL выбираются только из разрешённого списка.
*   [ ] При ошибке добавления второй позиции заказа в базе не остается ни заголовка, ни первой позиции.

Полная демонстрация и запуск: [JDBC и транзакции](../examples/lecture-16-jdbc-transactions/README.md). Дополнительные варианты: [банк заданий](../assignments/lecture-16.md).

Контракты JDBC: [Connection Java 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/Connection.html) и [PreparedStatement Java 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/PreparedStatement.html).
