# Лекция 23. Vaadin и Spring Boot прикладная архитектура

Версия для чтения. Основа: [рекомендации к лекции 23](lecture-23.md).

**Цель:** Связать Vaadin UI, сервисный слой и Spring Data без дублирования бизнес логики.

## Основные понятия

Vaadin View — адаптер пользовательского интерфейса. Она получает DTO, вызывает
use-case сервиса и отображает результат. Бизнес-правило не дублируется в listener,
иначе REST и UI начнут вести себя по-разному. JPA entity не хранится в UI session:
она может стать detached, раскрыть связи и увеличить память.

Spring создаёт route-компоненты и внедряет сервисы. Scope должен соответствовать
состоянию: singleton не хранит данные конкретного пользователя, UI scope живёт
в пределах вкладки, session scope — browser session. Необоснованное состояние в
scope усложняет кластеризацию и восстановление.

Route parameters делают URL воспроизводимым: карточка заказа `/orders/42` лучше
скрытого выбора в памяти списка. View валидирует формат параметра, сервис сообщает
об отсутствии, error handler переводит ситуацию в понятную страницу без выдачи
stack trace.

Интеграция Spring Security защищает navigation до создания содержимого и
проверяет методы сервиса. Маршрут, недоступный из меню, всё равно должен быть
закрыт при прямом URL. UI отображает разрешённые действия для удобства, но
серверная проверка остаётся источником истины.

Для фоновой задачи сохраняют ссылку на `UI` только в контролируемой области,
обновляют через `ui.access` и проверяют attachment. Push доставляет изменения,
но требует управления executor, ошибками и жизненным циклом. Неограниченный
поток на каждого пользователя недопустим.

Service тестируется без UI, view — browserless/component test, критический
маршрут — end-to-end. E2E-тестов мало: они медленнее и чувствительнее к окружению.

## От модели к решению

### Общий use case

REST и Vaadin могут вызывать один сервис создания заказа. Он проверяет инварианты, предметные права и транзакционную границу. View отвечает за форму, контроллер — за HTTP. Изменение скидки не требует двух реализаций.

DTO содержит нужные экрану значения, а не всю entity со связями. Это не переносит persistence context в UI-сессию. Данные экрана могут устареть: при сохранении нужны версия и обработка конфликта.

### Scope и маршрут

UI scope соответствует UI, обычно вкладке; VaadinSession scope — Vaadin-сессии. Route scope ограничивает состояние жизнью маршрута. Browser session и VaadinSession не во всех конфигурациях означают одно и то же. Singleton-сервис может обслуживать множество пользователей.

Id в URL делает карточку воспроизводимой, но остаётся недоверенным вводом. Проверяются формат, существование и право доступа. Скрытый пункт меню не запрещает прямой переход. Ограничение маршрута и проверка сервиса защищают разные уровни.

### Фоновые операции

В listener можно сохранить ссылку на текущий UI для ограниченной фоновой операции. В рабочем потоке UI.getCurrent обычно не указывает на нужную страницу. Изменения выполняются через ui.access, с учётом detach и отмены работы при закрытии страницы.

Push доставляет изменения без действия пользователя, если включён и настроен. Альтернатива — polling. Executor принадлежит приложению с управляемым жизненным циклом: бесконтрольный поток на каждое событие расходует ресурсы.

ProductView получает сервис конструктором и задаёт колонки явно. `findAll()` подходит только маленькому набору. Для большого списка загрузка и подсчёт используют одинаковые фильтры и устойчивую сортировку.

Тест сервиса проверяет предметный результат, компонентный — форму, E2E — критический браузерный путь. Отдельно проверяют прямой URL под пользователем без нужной роли.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 23](../examples/lecture-23-vaadin-spring-architecture/README.md).

```java
@com.vaadin.flow.router.Route("products")
public class ProductView extends com.vaadin.flow.component.orderedlayout.VerticalLayout {
    private final ProductService service;
    private final com.vaadin.flow.component.grid.Grid<ProductDto> grid =
        new com.vaadin.flow.component.grid.Grid<>(ProductDto.class, false);

    public ProductView(ProductService service) {
        this.service = service;
        grid.addColumn(ProductDto::name).setHeader("Название");
        add(grid);
        grid.setItems(service.findAll()); // учебный минимум; для больших каталогов — DataProvider с пагинацией
    }
}
```

В production `findAll()` в конструкторе View не масштабируется: используйте
`Grid.setItems(DataProvider.fromCallbacks(...))` или постраничный API сервиса.

## Разбор и проверка результата

### Карточка заказа по прямому адресу

Переход на /orders/42 начинается с проверки доступа к маршруту и параметра. Затем сервис проверяет право на конкретный заказ и возвращает DTO. Отсутствующий заказ превращается в понятное состояние страницы; технический stack trace остаётся в журнале.

Две вкладки могут иметь разные UI и редактировать разные объекты в одной пользовательской сессии. Если положить текущий заказ в слишком широкую область, переключение в одной вкладке повлияет на другую. Поэтому состояние редактирования привязывается к подходящему UI или маршруту.

При фоновом обновлении сохранённая ссылка на UI может пережить страницу. Проверка attachment полезна, но сама по себе не устраняет гонку отсоединения; обновление всё равно выполняется через предусмотренный механизм access с обработкой ситуации закрытия. Отмена ненужной задачи освобождает и серверные ресурсы, и удерживаемые ссылки.

## Типичные ошибки

- SQL или repository в View;
- singleton хранит текущего пользователя;
- доступ ограничен только видимостью кнопки;
- background thread меняет компонент без `UI.access`;
- десятки E2E-тестов вместо тестов слоёв.

## Самостоятельная работа

Добавить экран заказов, переход к карточке заказа, проверку ролей и тест критического пользовательского сценария.

**Рекомендации к решению.** Не хранить JPA entity в состоянии UI. Для фонового обновления получать UI safely и учитывать отсоединение страницы.

**Критерии приёмки.** Права проверяются на сервере; прямой переход по URL не обходит авторизацию; UI не выполняет SQL; основной сценарий подтвержден тестом.
