# Лекция 8. Исключения контракты и работа с ресурсами

Версия для чтения. Основа: [рекомендации к лекции 8](lecture-08.md).

**Цель:** Разделять ожидаемые ошибки и программные дефекты, не терять причину исключения.

## Основные понятия

Исключение сообщает, что метод не может нормально выполнить контракт. `Error`
обычно отражает серьёзную проблему среды, `Exception` — ситуацию приложения.
Checked-исключение требуется объявить или обработать; unchecked-наследники
`RuntimeException` компилятор не контролирует. Выбор зависит не от «важности», а
от того, способен ли вызывающий код разумно восстановиться.

Сообщение должно содержать контекст, но не секреты. При оборачивании исключения
первоначальную причину передают в конструктор. Иначе stack trace теряет место
исходного сбоя. Предметный тип исключения полезен, когда вызывающий код различает
сценарии, например `ProductNotFoundException` и `InsufficientStockException`.

`try-with-resources` закрывает любой `AutoCloseable` в обратном порядке даже при
исключении. Если и основная операция, и `close` падают, второе исключение
становится suppressed и доступно через stack trace. Ручной `finally` нужен реже и
легко скрывает исходную ошибку.

Перехват должен происходить на уровне, который способен добавить смысл или
восстановиться. `catch (Exception e) {}` уничтожает диагностику. Логировать и
сразу пробрасывать одно исключение на каждом слое тоже плохо: журнал получает
несколько одинаковых stack trace.

Контракт ресурса включает владение: кто открыл поток, тот обычно его закрывает.
Метод, получивший поток от вызывающего кода, не должен неожиданно закрывать его,
если это не указано явно.

**Подготовка к коллекциям (до лекции 9).** Рекомендуется самостоятельное задание:
класс `Student` (имя, группа), список `ArrayList<Student>`, фильтрация по группе,
сравнение с `HashSet` для уникальности. Так generics и коллекции вводятся на
практике до формального раздела про `Map`, `equals` и `hashCode`.

## От модели к решению

### Исключение как часть API

Чтение файла может закончиться корректным результатом, ошибкой открытия или ошибками отдельных записей. Пустой список не должен одновременно означать пустой файл и отсутствие прав на чтение: вызывающий код потеряет возможность принять решение.

Ошибка строки может стать структурированным результатом с номером строки, если допустимо продолжение. Ошибка открытия прерывает всю операцию. Сообщение включает контекст, а исходный IOException сохраняется в cause нового исключения.

### Управление ресурсами

Files.lines возвращает ленивый stream, связанный с открытым файлом. Терминальная операция count проходит по строкам, выход из try закрывает stream. Сам вызов терминальной операции не заменяет закрытие. Ошибка возможна не только при открытии, но и во время чтения; ленивое чтение может сообщить её через UncheckedIOException.

Если основной код и закрытие бросают исключения, try-with-resources сохраняет основное, а ошибку close добавляет в suppressed. Если основная операция успешна, ошибка закрытия сама становится основной. Ручной finally легко скрывает первоначальную причину.

Finally выполняется при обычном выходе, включая return и исключение. Но аварийное завершение процесса может не дать коду выполниться. Return из самого finally опасен: он способен заменить прежний результат или скрыть исключение.

### Где обрабатывать ошибку

Нижний слой знает техническую причину, сервис — предметное действие, граница приложения — сообщение пользователю. Одно исключение не обязательно логировать на каждом слое: достаточно сохранить причины и записать событие на границе окончательной обработки.

Checked-исключения заставляют обработать или объявить их, но не гарантируют разумную обработку. Unchecked-исключения тоже требуют документированного контракта. Решение зависит от сценариев вызывающего кода.

## Практический пример

Пример сохраняется в `LineCounter.java` и запускается командами `javac LineCounter.java` и `java LineCounter`. Путь к файлу можно передать аргументом; без аргумента читается `orders.txt`. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 8](../examples/lecture-08-exceptions-resources/README.md).

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class LineCounter {
    static long countLines(Path path) throws IOException {
        try (var lines = Files.lines(path)) {
            return lines.count();
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println(countLines(Path.of(args.length == 0 ? "orders.txt" : args[0])));
    }
}
```

## Разбор и проверка результата

### Два разных отказа чтения

Существующий пустой файл даёт countLines результат ноль. Несуществующий путь приводит к исключению. Эти исходы нельзя объединять в ноль: пользователь иначе не узнает, что источник вообще не был прочитан.

Метод открывает stream сам и потому закрывает его. Если бы он принимал уже открытый Reader, вопрос закрытия определялся бы контрактом владения. Неожиданное закрытие чужого ресурса может сломать следующий этап обработки.

Для импорта заказов полезен результат из двух частей: корректные записи и ошибки отдельных строк. Однако ошибка доступа к файлу не относится к ошибкам конкретной строки. Это сбой всей операции. Такое разделение помогает продолжать там, где это разрешено, и не выдавать частичный технический сбой за полноценный успешный импорт.

## Типичные ошибки

- пустой `catch`;
- перехват `Exception` там, где ожидается конкретный сбой;
- возврат пустого результата при ошибке чтения;
- создание нового исключения без исходной причины;
- незакрытый поток или JDBC-ресурс.

## Самостоятельная работа

Прочитать файл заказов, вернуть корректные строки и список ошибок с номерами строк. До реализации записать предусловия, постусловия и последствия метода, затем сравнить API, который скрывает ошибку открытия пустым результатом, с API, сохраняющим причину.

**Рекомендации к решению.** Ошибка одной строки не должна скрывать ошибки остальных. Ошибку открытия файла не подменять пустым результатом.

**Критерии приёмки.** Контракт метода описывает условия и последствия; ресурс закрывается автоматически; сообщения содержат контекст; первоначальная причина сохраняется при оборачивании; ошибка открытия не выглядит как успешный пустой файл.
