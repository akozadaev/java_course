# Лекция 18. Spring Core и Spring Boot

Версия для чтения. Основа: [рекомендации к лекции 18](lecture-18.md).

**Цель:** Понимать контейнер зависимостей и запускать минимальное Spring Boot приложение.

## Основные понятия

Inversion of Control означает, что жизненным циклом объектов и связыванием
зависимостей управляет контейнер. Dependency injection — способ передать объекту
его зависимости извне. Constructor injection делает обязательные зависимости
явными, позволяет использовать `final` поля и создавать класс в обычном unit
тесте без Spring.

Bean — объект, зарегистрированный в `ApplicationContext`. Component scanning
находит стереотипы `@Component`, `@Service`, `@Repository`, а методы `@Bean`
регистрируют объекты сторонних библиотек или явно настроенные компоненты.
Несколько реализаций одного интерфейса требуют `@Qualifier` или выбора primary.
Циклическая зависимость обычно сообщает о смешении ответственности.

`@SpringBootApplication` объединяет configuration, auto-configuration и component
scan. Starter задаёт согласованный набор зависимостей. Auto-configuration
включается по classpath, bean-ам и properties и отступает, если пользователь
предоставил свою настройку. Это соглашение, а не магия: condition report и
документация позволяют понять решение.

Конфигурация приходит из properties/YAML, окружения и аргументов. Profiles
выбирают набор bean-ов или свойств среды, но не должны разветвлять бизнес-логику.
Типизированный `@ConfigurationProperties` предпочтительнее множества `@Value`:
он группирует настройки и поддерживает validation.

Spring Boot 4 использует Spring Framework 7 и Jakarta API. Примеры старых курсов
с `javax.*` могут не компилироваться. Версии starter-зависимостей управляются BOM
родителя; вручную смешивать несовместимые версии Spring нельзя.

## От модели к решению

### Контейнер и обычные объекты

Без Spring приложение само создаёт repository, передаёт его сервису, а сервис — контроллеру. DI означает получение зависимостей извне. Spring переносит создание и связывание в ApplicationContext; сами классы могут оставаться обычными Java-классами.

Один конструктор обычно не требует Autowired. Зависимость хранится в final-поле, unit-тест создаёт сервис через new с fake или stub. Поиск ApplicationContext из каждого метода скрывает реальные зависимости.

### Регистрация и scope

Главный класс размещают в корневом пакете приложения: сканирование охватывает вложенные пакеты. Класс в соседнем пакете может остаться незарегистрированным даже с Service. Сначала проверяют регистрацию, а затем конструктор.

Singleton означает один экземпляр соответствующего bean в контейнере и не делает его потокобезопасным. Общий сервис не хранит в полях текущий заказ или имя клиента. Данные запроса передаются параметрами либо живут в подходящей области.

### Условия и конфигурация

Starter подключает библиотеки, auto-configuration регистрирует компоненты по условиям. Не каждая настройка отступает при любом пользовательском bean: важны конкретный тип и ConditionalOnMissingBean. При неожиданном поведении полезен conditions report.

ConfigurationProperties группирует настройки в типизированный объект, который можно валидировать при запуске. Профиль test задаёт отдельные настройки среды, но не оправдывает секреты в репозитории.

Пример показывает main и сервис, но greet сам по себе не вызывается. Нужен runner, тест или HTTP-контроллер следующей темы. Публичные классы сохраняются в разных файлах. Jakarta-пространства относятся к мигрировавшим API; пакеты JDK javax.sql и javax.crypto не переименовываются.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 18](../examples/lecture-18-spring-core-boot/README.md).

```java
// CatalogApplication.java
@org.springframework.boot.autoconfigure.SpringBootApplication
public class CatalogApplication {
    public static void main(String[] args) {
        org.springframework.boot.SpringApplication.run(CatalogApplication.class, args);
    }
}

// GreetingService.java — отдельный файл в том же пакете
@org.springframework.stereotype.Service
public class GreetingService {
    public String greet(String name) { return "Hello, " + name; }
}
```

## Разбор и проверка результата

### От запуска контекста к вызову сервиса

SpringApplication.run создаёт и подготавливает контекст. Наличие GreetingService в сканируемом пакете позволяет внедрить его в другой bean. Однако это не означает, что метод greet автоматически вызывается при старте. Вызов должен быть предусмотрен явно.

Чтобы проверить сервис без Spring, достаточно создать GreetingService и сравнить результат greet для заданного имени. Проверка регистрации bean — другая задача: она требует контекста. Такое разделение сохраняет быстрые тесты поведения и небольшое число проверок инфраструктуры.

Профиль задаётся извне, например аргументом `--spring.profiles.active=dev`. Сам профиль не должен менять смысл расчёта скидки или разрешать некорректные заказы. Он меняет подходящую инфраструктуру и параметры среды. Ошибка отсутствующей обязательной настройки лучше проявляется при запуске, чем при первом пользовательском запросе.

## Типичные ошибки

- field injection;
- получение bean через статический `ApplicationContext`;
- классы приложения вне корневого package scan;
- секреты в `application.properties` репозитория;
- версии Spring-зависимостей заданы независимо от BOM.

## Самостоятельная работа

Создать проект через Spring Initializr, добавить сервис и отдельные конфигурации dev и test.

**Рекомендации к решению.** Использовать внедрение через конструктор. Не получать bean вручную из ApplicationContext в прикладном коде.

**Критерии приёмки.** Приложение запускается mvn spring-boot:run; профиль задается извне; циклических зависимостей нет.
