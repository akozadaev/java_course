# Лекция 22. Vaadin Flow основы пользовательского интерфейса

Версия для чтения. Основа: [рекомендации к лекции 22](lecture-22.md).

**Цель:** Создать серверный UI на Java и понять жизненный цикл компонентов.

## Основные понятия

Vaadin Flow позволяет описывать web UI Java-компонентами. Сервер хранит состояние
UI и синхронизирует изменения с браузером. Это ускоряет разработку внутренних
систем, но означает session state, сетевые round trips и необходимость не
блокировать UI thread долгой работой.

`@Route` связывает компонент с URL. Навигация должна иметь стабильные маршруты,
поддерживать параметры и browser history. Layout компонует дочерние элементы;
размеры и responsive-поведение задаются осознанно, а не цепочкой случайных
`setWidth`.

Компоненты `TextField`, `Button`, `Grid`, `FormLayout` имеют серверное API и
клиентское представление. Listener вызывается на сервере. Частые события поля
могут создавать много запросов; ValueChangeMode и debounce выбираются по задаче.

`Binder<T>` связывает поля формы с объектом, преобразует типы и проверяет
значения. Field-level validation даёт быструю обратную связь, а сервис повторно
защищает бизнес-инварианты. Успешное сохранение очищает или обновляет форму только
после подтверждения сервиса.

`Grid` не должен загружать миллион строк. Callback DataProvider или pageable
service предоставляет ленивые страницы, фильтр и стабильную сортировку. Колонки
задают явно, чтобы не показать служебные/чувствительные свойства.

Доступность включает label, keyboard navigation, focus order, достаточный
контраст и сообщение об ошибке не только цветом. Lumo предоставляет основу, но
кастомные стили всё равно проверяются.

## От модели к решению

### Серверная модель интерфейса

Flow хранит Java-компоненты на сервере. Нажатие кнопки вызывает listener, изменения синхронизируются с браузером. Это упрощает вызов Java-сервисов, но требует учитывать память сессии и сетевую задержку.

Путь Route задаётся без начального слеша; пустая строка означает корневую страницу. В примере кнопка читает TextField и меняет Span через setText. Не следует заменять текст вставкой непроверенного HTML.

### Форма и Binder

Binder связывает поля, преобразования и проверки. BeanValidationBinder умеет учитывать Bean Validation при подходящей модели. В buffered-подходе readBean заполняет форму, а writeBeanIfValid переносит значения после проверки: это удобно для «Сохранить» и «Отмена».

`setBean` может сразу переносить изменения в bean. Если bean принадлежит общему состоянию, отмена формы уже не сводится к закрытию окна. Отдельная модель формы позволяет применять изменения через сервис после проверки.

### Список и отзывчивость

`setItems` с маленькой коллекцией подходит для первой демонстрации. Большой каталог требует ленивой загрузки, устойчивой сортировки и согласованного подсчёта. Виртуализация строк браузера не отменяет затрат сервера, если заранее загрузить всё.

Ошибка поля имеет текст и связь с компонентом, а не только цвет. После отказа введённые данные сохраняются для исправления. Клавиатурой должны быть доступны и поля, и действия.

У Flow нет отдельного постоянного системного потока на каждую страницу. Обработчики выполняются серверными потоками с блокировкой сессии. Долгая операция в listener ухудшает отзывчивость; её выносят в управляемую фоновую задачу.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 22](../examples/lecture-22-vaadin-basics/README.md).

```java
@com.vaadin.flow.router.Route("")
public class MainView extends com.vaadin.flow.component.orderedlayout.VerticalLayout {
    public MainView() {
        var name = new com.vaadin.flow.component.textfield.TextField("Имя");
        var output = new com.vaadin.flow.component.html.Span();
        var button = new com.vaadin.flow.component.button.Button("Поздороваться",
            event -> output.setText("Здравствуйте, " + name.getValue()));
        add(name, button, output);
    }
}
```

## Разбор и проверка результата

### Последовательность сохранения формы

Пользователь вводит название и цену, Binder проверяет форму. При ошибке сохранение не вызывается, а поле получает понятное сообщение. При успешной локальной проверке View передаёт данные сервису. Сервис может отказать по актуальному бизнес-правилу, например из-за занятого имени.

Только подтверждённое создание приводит к обновлению Grid и очистке формы. Если очистить поля до ответа сервиса, при отказе пользователь потеряет ввод. Если обновить список локально без подтверждения, интерфейс может показать товар, которого нет в хранилище.

Обновление страницы и повторное открытие маршрута должны показывать состояние сервиса, а не только оставшийся в памяти UI список. Это различие особенно важно в серверной модели Flow: наличие строки в Grid не является доказательством сохранения в БД.

## Типичные ошибки

- repository вызывается прямо из View;
- entity хранится как bean формы;
- весь список передан в `grid.setItems`;
- ошибка показана только Notification без связи с полем;
- долгий запрос блокирует UI.

## Самостоятельная работа

Создать страницу списка товаров и форму добавления с Binder и проверкой полей.

**Рекомендации к решению.** Не помещать доступ к БД прямо в View. View вызывает сервис; сервис проверяется отдельно модульными тестами.

**Критерии приёмки.** Маршрут открывается; форма показывает ошибки до сохранения; клавиатурная навигация работает; Grid обновляется после успешного создания.
