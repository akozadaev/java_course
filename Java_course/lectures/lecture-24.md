# Лекция 24. Сборка контейнеризация и итоговый проект

Версия для чтения. Основа: [рекомендации к лекции 24](lecture-24.md).

**Цель:** Собрать воспроизводимый релиз и защитить архитектурные решения проекта.

## Основные понятия

Релиз начинается с воспроизводимой проверки: `mvn clean verify` на чистом клоне.
Executable jar содержит приложение и запускается одинаковой командой. Версии
плагинов и зависимостей фиксированы, generated-файлы не подменяют исходники, а
сборка не зависит от локальных секретов IDE.

Контейнер упаковывает процесс и его runtime, но не является виртуальной машиной.
Образ строят слоями: редко меняющаяся runtime/dependency часть кэшируется отдельно
от приложения. Multi-stage build может компилировать проект и переносить только
результат в минимальный runtime image. Контейнер запускают не от root, файловую
систему по возможности делают read-only.

Конфигурация twelve-factor поступает извне. Один образ проходит среды без
пересборки. Docker Compose описывает приложение, PostgreSQL, сеть, volumes и
healthcheck для локального/учебного запуска. `depends_on` сам по себе не всегда
означает готовность БД: приложение должно корректно повторять подключение, а
readiness отражает готовность обслуживать запросы.

Graceful shutdown прекращает принимать новую работу, завершает текущие запросы и
освобождает ресурсы в пределах timeout. Liveness отвечает, нужно ли перезапустить
процесс; readiness — можно ли направлять трафик. Неверная liveness-проверка БД
может вызвать каскадные перезапуски при внешнем сбое.

CI выполняет compile, tests, static checks, сборку и анализ зависимостей. Отчёт об
уязвимости требует triage: совпадение версии ещё не доказывает эксплуатируемость,
но игнорировать его нельзя. SBOM и регулярные обновления делают состав артефакта
наблюдаемым.

Защита проекта проверяет не количество технологий, а сквозные сценарии и
обоснование решений. Студент должен развернуть систему из чистого клона,
продемонстрировать ошибочный и успешный путь, изменить одно правило и объяснить
результат тестов.

## От модели к решению

### Один артефакт для разных сред

Wrapper фиксирует Maven, параметры компилятора — Java release. Строгая воспроизводимость зависит также от JDK, плагинов, репозиториев и метаданных упаковки. Одинаковая команда не гарантирует побайтового совпадения без настройки.

Spring Boot plugin создаёт исполняемый JAR с зависимостями. Имя определяется pom.xml; Dockerfile копирует именно этот файл. Обычный тонкий JAR может не запуститься через java -jar.

### Контейнер и состояние

Минимальный Dockerfile копирует целый JAR в runtime-образ и запускает отдельного пользователя. Он не разделяет библиотеки и классы по слоям: для этой оптимизации нужна другая раскладка содержимого либо поддерживаемая сборка образа.

Тег может быть изменяемым; строго фиксированный релиз использует digest и управляемые обновления. Секреты передаются при запуске, а не запекаются в образ. PostgreSQL хранит данные в volume независимо от контейнера приложения.

### Готовность и остановка

`depends_on` с condition service_healthy позволяет дождаться healthcheck БД при старте. Последующую потерю связи приложение обрабатывает самостоятельно. Readiness-группа Boot не обязана включать БД автоматически: её состав настраивается под архитектуру.

Liveness отвечает, нужен ли перезапуск, readiness — можно ли направлять запросы. Перезапуск всех приложений при отказе общей БД часто увеличивает нагрузку. Graceful shutdown прекращает новую работу и даёт текущей ограниченное время завершиться.

### Приёмка

README позволяет собрать проект, передать настройки и пройти сквозной сценарий: создать товар, оформить заказ, увидеть его в UI. Затем проверяется отказ — неверные данные, недостаток прав или конфликт версии.

Запуск с пустой БД проверяется в отдельном учебном окружении и не требует удаления существующих volumes с полезными данными. CI автоматизирует шаги; сообщение об уязвимой зависимости требует оценки применимости и контролируемого обновления.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 24](../examples/lecture-24-final-catalog-app/README.md).

```bash
# Запуск приложения после сборки
mvn clean verify
java -jar target/catalog-0.0.1-SNAPSHOT.jar

```

Минимальный `Dockerfile` (имя JAR должно совпадать с `pom.xml`):

```dockerfile
FROM eclipse-temurin:25-jre
WORKDIR /app
RUN useradd -r -u 10001 appuser
COPY target/catalog-0.0.1-SNAPSHOT.jar app.jar
USER appuser
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

## Разбор и проверка результата

### Что доказывает чистый запуск

Если приложение запускается только на старом volume, это может означать, что нужную таблицу когда-то создали вручную. Запуск в отдельном окружении с пустой БД показывает, что миграции действительно создают схему. Обновление существующей версии проверяется отдельно: создание с нуля не доказывает корректность обновления данных.

После остановки и повторного старта контейнера приложения сохранённый заказ должен остаться в PostgreSQL. Это проверяет вынесенное хранение, но не заменяет резервное копирование и восстановление. Volume сохраняет данные при обычной замене контейнера, а не при любой возможной аварии.

Для итогового показа важны команда запуска, фактический результат и объяснение границ. Список подключённых технологий сам по себе не подтверждает ни разграничение доступа, ни атомарность заказа, ни воспроизводимость релиза. Каждое заявленное свойство связывается с конкретным сценарием и проверкой.

## Типичные ошибки

- сборка работает только из IDE;
- secret запечён в image;
- процесс контейнера работает root;
- health всегда возвращает UP;
- Compose использует данные, вручную созданные ранее.

## Самостоятельная работа

Завершить учебный проект: REST API, PostgreSQL, Vaadin UI, авторизация, тесты, миграции, Docker Compose и README.

**Рекомендации к решению.** Проверить чистое развертывание на другой машине. В README указать предпосылки, команды запуска, учетные записи для демонстрации и архитектурные ограничения.

**Критерии приёмки.** mvn verify и docker compose up проходят из чистого клона; приложение не запускается от root в контейнере; health отражает готовность БД; все обязательные сценарии демонстрируются.
