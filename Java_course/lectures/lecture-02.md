# Лекция 2. Оформление кода и инструменты проекта

Версия для чтения. Основа: [рекомендации к лекции 2](lecture-02.md).

**Цель:** Оформлять код по единым правилам и собирать проект Maven.

## Основные понятия

Код чаще читают, чем пишут. Единый стиль снижает когнитивную нагрузку: имя
показывает назначение, структура метода — ход решения, а автоматический
форматировщик устраняет споры о пробелах. Классы именуют существительными в
`UpperCamelCase`, методы и переменные — действиями или понятиями в
`lowerCamelCase`, константы — `UPPER_SNAKE_CASE`.

Комментарий не должен повторять код. Полезный комментарий объясняет причину,
ограничение или неочевидный компромисс. Javadoc описывает контракт публичного
API: допустимые данные, результат, исключения и важные побочные эффекты. Детали
реализации в контракт не включают, иначе рефакторинг потребует переписывать
документацию.

Maven задаёт стандартную структуру: `src/main/java` для приложения,
`src/test/java` для тестов, `pom.xml` для координат, зависимостей и плагинов.
Фазы образуют цепочку: `compile`, `test`, `package`, `verify`, `install`.
Выполнение `verify` включает более ранние фазы. Артефакт появляется в `target`,
который не коммитят в Git.

Зависимость имеет координаты `groupId:artifactId:version`. Версии должны быть
воспроизводимыми; диапазоны и `LATEST` для учебного проекта недопустимы.
Wrapper фиксирует Maven для команды, но на базовом курсе допустима системная
версия Maven 3.9.x; точный номер сверяют на дату проведения курса или печати
пособия (`mvn --version`).

Git хранит историю исходников, а не сгенерированные результаты. Минимальный цикл:
`git status`, `git diff`, `git add`, `git commit`. Перед коммитом выполняют
`mvn verify`. Отладчик помогает поставить breakpoint, пройти код по шагам и
посмотреть значения; он дополняет, но не заменяет тесты.

Stack trace читают сверху вниз: первая строка — тип и сообщение исключения,
первые строки с пакетами проекта — место проявления дефекта, блок `Caused by` —
исходная причина. Не следует начинать с последней строки или удалять исключение.

## От модели к решению

### Стиль как часть контракта

Имя `calculateDeliveryCost` сообщает больше, чем `process`: оно называет результат действия. Краткость метода сама по себе не доказывает качество. Полезное разделение выделяет самостоятельные понятия: проверку входа, расчёт и форматирование. Форматировщик упорядочивает оформление, а статический анализ ищет определённые классы проблем. Правильность алгоритма требует отдельных проверок.

Javadoc расчёта цены должен объяснять единицы измерения. Значение `1990` означает 19 рублей 90 копеек только при явно принятом контракте хранения копеек. Нужны также допустимый диапазон процента, правило округления и поведение при переполнении. Комментарий «умножаем цену на процент» этих вопросов не решает.

### Сборка и расчёт

Maven выполняет фазы жизненного цикла через плагины. `test` включает компиляцию приложения и тестов; `package` добавляет упаковку; `verify` выполняет более ранние фазы и привязанные проверки. Название фазы не гарантирует, что форматировщик или интеграционные тесты настроены: соответствующий плагин должен быть подключён.

Обычный JAR не обязательно запускается через `java -jar`: ему нужна запись главного класса в manifest, а для внешних библиотек — подходящий способ доставки зависимостей. Каталог `target` содержит результаты сборки, которые можно получить заново из исходников.

В примере цена хранится в минимальных денежных единицах, дробная часть результата отбрасывается целочисленным делением. Умножение может переполнить `long` ещё до деления. Поэтому используется `Math.multiplyExact`: переполнение становится исключением вместо скрытого неверного результата. Для больших диапазонов может потребоваться BigInteger или BigDecimal.

Stack trace показывает место проявления и цепочку причин. Строка своего кода может лишь вызывать библиотеку, поэтому важно читать `Caused by`. Отладчик позволяет проверить гипотезу о значениях, а воспроизводимый тест закрепляет исправление.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 2](../examples/lecture-02-maven-code-quality/README.md).

```java
public final class PriceCalculator {
    /** Возвращает цену после скидки от 0 до 100 процентов. */
    public long applyDiscount(long price, int percent) {
        if (price < 0 || percent < 0 || percent > 100) {
            throw new IllegalArgumentException("Invalid price or percent");
        }
        return Math.multiplyExact(price, 100L - percent) / 100;
    }
}

// Maven:
// mvn test
// mvn package
```

## Разбор и проверка результата

### Разбор числового результата

Для цены 1990 копеек и скидки 15% расчёт даёт `1990 × 85 / 100 = 1691`: после деления получаются целые копейки. Для цены 1 копейка и скидки 50% результат равен нулю по выбранному правилу отбрасывания дробной части. Если требуется округление до ближайшей копейки, алгоритм должен быть другим — это изменение контракта, а не форматирования.

Значение процента 101 отклоняется до арифметики. Максимальное значение long с ненулевым множителем может вызвать ArithmeticException даже тогда, когда окончательный математический результат после деления поместился бы в long. Такой предел промежуточного вычисления следует понимать и документировать.

Рефакторинг имён и отступов сохраняет результаты на тех же входах. Изменение правила округления уже меняет поведение и требует согласования требований и проверок. Это позволяет отделить косметическую правку от исправления алгоритма.

## Типичные ошибки

- огромный метод с именем `process`;
- комментарий `// увеличиваем i` перед `i++`;
- зависимости без фиксированных версий или BOM;
- коммит каталогов `target` и настроек IDE;
- подавление stack trace сообщением «что-то сломалось».

## Самостоятельная работа

Создать Maven-проект с классом расчета стоимости, Javadoc и автоматическим форматированием.

**Рекомендации к решению.** Публичный API описать через контракт: входные значения, результат и исключения. Не комментировать очевидные операции.

**Критерии приёмки.** mvn verify завершается успешно; имена отражают назначение; форматирование воспроизводимо; нет неиспользуемых импортов.
