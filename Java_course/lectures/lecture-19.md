# Лекция 19. REST API на Spring MVC

Версия для чтения. Основа: [рекомендации к лекции 19](lecture-19.md).

**Цель:** Создавать контроллеры, проверять входные DTO и единообразно возвращать ошибки.

## Основные понятия

Spring MVC преобразует HTTP-запрос в вызов метода контроллера. `@RestController`
возвращает представление в теле ответа, mapping-аннотации связывают метод и URI,
`@RequestBody`, `@PathVariable`, `@RequestParam` извлекают данные. Контроллер
координирует протокол и сервис, но не содержит бизнес-правила и SQL.

Request DTO отделяет внешний контракт от domain/entity. Клиент не должен иметь
возможность прислать серверный id, роль или вычисляемое поле только потому, что
они есть в entity. Response DTO стабилизирует API и предотвращает случайную
сериализацию ленивых связей. Mapping можно писать явно; автоматический mapper
оправдан лишь при контролируемых правилах.

Bean Validation проверяет форму данных через `@NotBlank`, `@Positive`,
`@Size` и пользовательские constraints. Аннотация `@Valid` запускает проверку
вложенного DTO. Бизнес-конфликт, например недостаток остатка, не является простой
валидацией поля и проверяется сервисом.

`ResponseEntity` управляет статусом и заголовками. Создание возвращает 201 и
желательно `Location`; удаление может вернуть 204. `@ControllerAdvice`
централизует перевод исключений в единый error DTO. Stack trace остаётся в
серверном журнале и не выдаётся клиенту.

Pagination ограничивает объём ответа. Параметры page/size имеют максимальный
size, сортировка разрешается только по известным полям. OpenAPI документирует
контракт, но сгенерированная схема не заменяет проверку поведения MockMvc-тестом.

## От модели к решению

### Путь запроса

DispatcherServlet выбирает обработчик по методу и пути, преобразует вход и вызывает контроллер. JSON читает message converter: неверный синтаксис может дать ошибку ещё до вызова метода. Для Bean Validation нужна соответствующая зависимость, а не только аннотации.

`@Valid` запускает проверку ограничений DTO и каскадную проверку вложенных объектов при подходящих аннотациях. `@Positive` отклоняет и ноль, и отрицательную цену. Если бесплатный товар допустим, подходит `@PositiveOrZero`. В примере цена выражена в минимальных денежных единицах.

### Границы ответственности

Клиент передаёт название и цену, сервер назначает id. Поэтому id отсутствует во входном DTO. Отдельная модель запроса предотвращает случайное присваивание роли, владельца или других внутренних полей.

Сервис сохраняет инварианты независимо от REST или Vaadin. Уникальность имени может потребовать ограничения БД: предварительный поиск сам по себе не защищает от конкурентной вставки.

### Ответ и проверка

Создание обычно возвращает 201 и Location нового ресурса. Ответ 204 не содержит тела. Ошибки ввода, отсутствия и конфликта различаются статусами. Единый DTO ошибки или ProblemDetail содержит публичный контракт без SQL и stack trace.

В примере id всегда равен единице, а состояние не сохраняется. Это демонстрация преобразования запроса и ответа. В практике заглушка заменяется сервисом: два успешных создания должны приводить к различимым ресурсам.

MockMvc проверяет HTTP-уровень без настоящего сетевого порта. Тест проверяет статус, Content-Type, поля ответа и отсутствие вызова создания при неверном теле. OpenAPI должен отражать фактические ограничения и ответы.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 19](../examples/lecture-19-spring-mvc-rest/README.md).

```java
record CreateProductRequest(
    @jakarta.validation.constraints.NotBlank String name,
    @jakarta.validation.constraints.Positive long price
) {}

record ProductResponse(long id, String name, long price) {}

@org.springframework.web.bind.annotation.RestController
@org.springframework.web.bind.annotation.RequestMapping("/api/products")
class ProductController {
    @org.springframework.web.bind.annotation.PostMapping
    org.springframework.http.ResponseEntity<ProductResponse> create(
        @jakarta.validation.Valid @org.springframework.web.bind.annotation.RequestBody CreateProductRequest body) {
        long id = 1L; // в приложении id назначает сервис или БД
        var response = new ProductResponse(id, body.name(), body.price());
        return org.springframework.http.ResponseEntity.created(
            java.net.URI.create("/api/products/" + id)).body(response);
    }
}
```

## Разбор и проверка результата

### Один контракт, несколько сценариев

Для POST /api/products с непустым названием и положительной ценой пример отвечает 201 и Location /api/products/1. Пустое название должно дать 400 при работающей Bean Validation. Неверный JSON тоже даёт ошибку ввода, но возникает на этапе преобразования тела, поэтому формат ответа нужно согласовать с общим обработчиком ошибок.

Get неизвестного товара в полноценной практике даёт 404. Повтор уникального имени может дать 409, если уникальность является требованием. Нельзя выбирать статус только по типу технического исключения без понимания предметной причины.

Для списка `page=0&size=20` означает контракт первой страницы по выбранной нумерации. Размер ограничивают сверху, отрицательные значения отклоняют. Сортировка по разрешённому полю и вторичному id делает порядок устойчивым, иначе элементы на соседних страницах могут повторяться или пропадать даже без ошибок сериализации.

## Типичные ошибки

- JPA entity в request/response;
- `@Valid` забыта;
- вся логика в контроллере;
- 500 для ожидаемого отсутствия ресурса;
- неограниченный `size` пагинации.

## Самостоятельная работа

Реализовать CRUD API каталога с валидацией и глобальным обработчиком ошибок.

**Рекомендации к решению.** Не отдавать JPA entity напрямую. Ошибка должна содержать стабильный код, человекочитаемое сообщение и поля с нарушениями.

**Критерии приёмки.** Контроллер проверен MockMvc; успешное создание возвращает 201; неверные данные возвращают 400; отсутствующий объект - 404.
