# Лекция 12. Файлы потоки NIO и сериализация данных

Версия для чтения. Основа: [рекомендации к лекции 12](lecture-12.md).

**Цель:** Читать и записывать файлы без утечек ресурсов и небезопасной Java serialization.

## Основные понятия

`Path` — платформонезависимое описание пути, `Files` — операции над файловой
системой. Относительный путь разрешается от рабочего каталога процесса, который
может отличаться в IDE, тесте и контейнере. Для важного файла логируйте или
проверяйте абсолютный нормализованный путь.

Байтовые потоки работают с произвольными данными, символьные — с текстом через
кодировку. UTF-8 следует указывать явно на границах. Reader и Writer преобразуют
между байтами и символами; Buffered-варианты сокращают число системных вызовов.
Закрытие ресурса и обработка частичной записи входят в контракт операции.

`Files.readString` удобен для небольшого файла, `Files.lines` обрабатывает строки
лениво и требует закрытия, channels и ByteBuffer дают более низкоуровневый
контроль. Нельзя объявить потоковую обработку автоматически более быстрой:
выбор зависит от размера, памяти и характера преобразования.

Java native serialization связывает данные с реализацией классов и опасна для
недоверенного входа. Для обмена используют явный формат, например JSON. Jackson
сопоставляет JSON и DTO, но вход всё равно нужно валидировать: успешный parsing
не гарантирует допустимость бизнес-данных.

Надёжная запись выполняется во временный файл, после успеха файл атомарно
перемещается на целевой путь, если файловая система это поддерживает. Тогда сбой
не выдаёт частичный отчёт за готовый.

## От модели к решению

### Путь не равен файлу

Path.of сам по себе ничего не читает и не создаёт. `normalize()` убирает синтаксические точки и двойные точки, но не проверяет существование и не разрешает символические ссылки. `toRealPath()` обращается к файловой системе и может завершиться исключением.

Рабочий каталог влияет на относительный путь. Ошибка «файл не найден» может означать неверное предположение о каталоге запуска. Пользовательский путь требует ограничения допустимой области; одной нормализации недостаточно против всех способов выхода через символические ссылки.

### Текст и данные

Одинаковые байты дают разные символы при разных кодировках. Явный UTF-8 согласует запись и чтение. `readString` загружает содержимое целиком; для больших файлов нужен контролируемый последовательный обход или другой подход с ограниченной памятью.

Корректный JSON может содержать товар с пустым названием и отрицательной ценой. Поэтому импорт делится на чтение, разбор DTO, валидацию и применение. При пакетном импорте заранее решают, допустим ли частичный результат.

### Публикация отчёта

`writeString` с TRUNCATE_EXISTING сразу обнуляет существующий файл. Это простой пример ввода-вывода, а не защищённая публикация: при ошибке записи старое содержимое может потеряться.

Для надёжной публикации временный файл создают рядом с целевым, записывают и закрывают, затем перемещают с ATOMIC_MOVE, если файловая система поддерживает операцию. Замена существующего назначения при атомарном переносе зависит от провайдера; поведение проверяют на целевой системе. При AtomicMoveNotSupportedException нельзя молча обещать атомарность обычного переноса.

Атомарная видимость имени не равна сохранности при отключении питания. Для долговечности нужны дополнительные гарантии файловой системы и синхронизация записи. В учебной задаче важно отличать готовый отчёт от временного и явно сообщать ошибку публикации.

## Практический пример

Пример сохраняется в `FileDemo.java` и запускается командами `javac FileDemo.java` и `java FileDemo`. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 12](../examples/lecture-12-nio-json/README.md).

```java
import java.nio.charset.StandardCharsets;
import java.nio.file.*;

public class FileDemo {
    public static void main(String[] args) throws Exception {
        var path = Path.of("report.txt");
        Files.writeString(path, "Готово\n", StandardCharsets.UTF_8,
            StandardOpenOption.CREATE, StandardOpenOption.TRUNCATE_EXISTING);
        System.out.print(Files.readString(path, StandardCharsets.UTF_8));
    }
}
```

## Разбор и проверка результата

### Что делает минимальная запись

Пример создаёт report.txt в рабочем каталоге или заменяет его содержимое строкой «Готово» с переводом строки. Последующее чтение использует ту же кодировку и печатает записанное. Повторный запуск не добавляет новую строку в конец: TRUNCATE_EXISTING выбирает замену.

Для добавления нужен другой режим, например APPEND, но он тоже не делает несколько конкурентных записей автоматически одной атомарной бизнес-операцией. Способ синхронизации и допустимость смешивания записей определяются отдельно.

При JSON-импорте полезно сохранить номер или путь проблемного поля. «Неверный файл» сообщает меньше, чем «у товара 3 поле price отрицательно». При этом сообщение не должно раскрывать секретное содержимое или внутреннюю структуру сервера. Техническая причина остаётся доступной для диагностики.

## Типичные ошибки

- зависимость от неявной кодировки;
- чтение огромного файла целиком;
- относительный путь без понимания рабочего каталога;
- десериализация недоверенного `ObjectInputStream`;
- запись прямо в итоговый файл без обработки сбоя.

## Самостоятельная работа

Импортировать JSON-файл товаров, проверить данные и экспортировать текстовый отчет в UTF-8.

**Рекомендации к решению.** Разделить чтение, преобразование и запись. Для большого файла обсудить потоковую обработку вместо чтения всего содержимого в память.

**Критерии приёмки.** Кодировка указана явно; поврежденный JSON дает диагностическую ошибку; частично записанный итоговый файл не выдается за успешный результат.
