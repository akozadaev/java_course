# Лекция 6. Классы объекты записи и неизменяемость

Версия для чтения. Основа: [рекомендации к лекции 6](lecture-06.md).

**Цель:** Проектировать состояние объекта и поддерживать его инварианты.

## Основные понятия

Класс объединяет состояние и операции, поддерживающие допустимость этого
состояния. Инвариант — условие, истинное после конструктора и после каждого
публичного метода. Если объект товара не может иметь отрицательную цену, проверка
должна находиться у границы создания, а не повторяться в каждом вызывающем коде.

Модификаторы доступа управляют областью видимости. Поля обычно `private`, а
публичный API минимален. `static` относится к классу, экземплярный член — к
конкретному объекту. Избыточное глобальное изменяемое `static`-состояние усложняет
тесты и создаёт проблемы параллельности.

Конструктор создаёт объект в согласованном состоянии. `this` обозначает текущий
экземпляр. В классическом неизменяемом классе поля объявляют `final`, проверяют
параметры и не предоставляют mutator-методы. Но `final` запрещает смену ссылки, а
не изменение объекта по этой ссылке.

`record` подходит для прозрачных носителей данных: компилятор создаёт компоненты,
конструктор, `equals`, `hashCode` и `toString`. Компактный конструктор проверяет и
нормализует значения до присваивания. Record не делает вложенную коллекцию
неизменяемой автоматически — требуется `List.copyOf` или защитная копия.

Неизменяемость упрощает совместное использование, кэширование и рассуждение о
коде. Недостаток — изменение моделируется созданием нового объекта. Для
идентичности сущностей и жизненного цикла иногда уместен обычный класс, а для
значений и DTO — record.

## От модели к решению

### Почему одних private-полей мало

Инкапсуляция означает сохранение допустимого состояния через все доступные операции. Если конструктор проверяет цену, а setter позволяет поставить отрицательную, инвариант нарушается. Getter внутреннего изменяемого списка даёт ещё один способ обойти проверки.

`final List<OrderLine> lines` запрещает присвоить другой список, но не запрещает `lines.clear()`. Для снимка набора позиций подходит List.copyOf. Копия поверхностная: изменяемые позиции всё ещё можно поменять. Надёжная модель использует неизменяемые позиции либо копирует их.

### Что создаёт record

В компактном конструкторе Product параметр name сначала проверяется и нормализуется, затем компилятор присваивает его компоненту. Метод доступа называется `name()`, а не `getName()`. Автоматические equals и hashCode используют компоненты, поэтому для цены BigDecimal сохраняется различие масштабов.

Record удобен для значения, которое определяется всеми компонентами. Для сущности с устойчивым идентификатором и изменяемым жизненным циклом может подойти обычный класс. Выбор следует модели равенства и поведения.

### Конструктор и фабрика

Конструктор имеет имя класса и не объявляет возвращаемый тип. Статическая фабрика `Order.of(lines)` может назвать способ создания и скрыть детали. Фабрика всё равно должна вести к проверкам инвариантов; она не оправдывает другой, обходящий проверки способ создания.

Стоимость позиции вычисляется из цены и количества. Количество должно быть положительным, цена — неотрицательной; валюта и округление согласуются отдельно. Исторический заказ обычно хранит цену на момент покупки, а не каждый раз берёт текущую цену каталога.

Неизменяемость упрощает совместное использование объекта. Она не делает автоматически потокобезопасным сервис с изменяемым хранилищем таких объектов: его состояние требует отдельного решения.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 6](../examples/lecture-06-immutable-domain/README.md).

```java
import java.math.BigDecimal;
import java.util.Objects;

public record Product(long id, String name, BigDecimal price) {
    public Product {
        if (id <= 0) throw new IllegalArgumentException("id");
        name = Objects.requireNonNull(name, "name").strip();
        var nonNullPrice = Objects.requireNonNull(price, "price");
        if (name.isEmpty() || nonNullPrice.signum() < 0) {
            throw new IllegalArgumentException("name or price");
        }
        price = nonNullPrice;
    }
}
```

## Разбор и проверка результата

### Проверка защитной копии

Пусть вызывающий код создаёт ArrayList позиций и передаёт его в Order. Если конструктор просто сохраняет ссылку, последующий clear исходного списка опустошит заказ. Если конструктор делает List.copyOf, внешний список можно менять без изменения структуры заказа.

Возвращаемая неизменяемая коллекция отклонит add, но это ещё не доказывает глубокую неизменяемость. Изменяемый объект позиции мог быть передан в оба списка и сохранить общий доступ. Поэтому тест рассматривает отдельно изменение списка и изменение элемента.

Для Product пустое имя после strip недопустимо, как и отрицательная цена; нулевая цена в примере разрешена. Это предметное решение. Если позже появится требование обязательной положительной цены, меняется проверка инварианта и соответствующие сценарии, а не только текст ошибки в интерфейсе.

## Типичные ошибки

- публичные изменяемые поля;
- setter, позволяющий нарушить инвариант;
- хранение переданного изменяемого списка без копии;
- использование record для объекта с богатым изменяемым жизненным циклом;
- смешение идентичности по `id` и равенства всех полей.

## Самостоятельная работа

Сравнить две версии `Order`: первая сохраняет переданный изменяемый список и возвращает его наружу, вторая использует защитную копию. Для второй версии добавить именованный фабричный метод `Order.of(...)` и вычисление стоимости позиции.

**Рекомендации к решению.** Записать инварианты до кода. Проверки поместить в конструкторы, чтобы недопустимый объект нельзя было создать.

**Критерии приёмки.** Изменение исходного списка после создания заказа не меняет заказ; полученную коллекцию нельзя изменить; имя фабрики объясняет способ создания; отрицательные значения отклоняются; денежные вычисления используют BigDecimal.
