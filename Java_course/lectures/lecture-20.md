# Лекция 20. Spring Data JPA миграции и транзакции

Версия для чтения. Основа: [рекомендации к лекции 20](lecture-20.md).

**Цель:** Сопоставлять предметную модель и реляционные данные без скрытых проблем запросов.

## Основные понятия

JPA сопоставляет объекты и реляционные строки, но не превращает БД в коллекцию.
Entity имеет идентичность и состояния transient, managed, detached, removed.
Изменение managed entity обнаруживается dirty checking при flush. Flush отправляет
SQL, но commit определяет успешное завершение транзакции.

Entity требует `@Entity`, `@Id` и доступного JPA конструктора. Связи
`@ManyToOne`, `@OneToMany` описывают направление объектной навигации; owning side
управляет foreign key. Cascade и orphan removal имеют сильную семантику и не
включаются автоматически «для удобства».

Spring Data repository создаёт реализацию интерфейса, но производные имена
методов не отменяют понимание SQL. Lazy-связь может потребовать загрузки при обращении; в Hibernate вне доступного контекста это может вызвать `LazyInitializationException`. Eager не является универсальным
исправлением: он создаёт лишние данные и N+1. Для use case выбирают fetch join,
entity graph или projection.

`@Transactional` задаёт границу unit of work обычно на публичном методе сервиса.
Вызов метода того же объекта обходит proxy и может не применить аннотацию.
Checked-исключения по умолчанию не всегда вызывают rollback — правила следует
понимать и при необходимости задавать явно.

Миграции Flyway — единственный источник схемы; `ddl-auto=validate` проверяет
соответствие. `@Version` реализует optimistic locking: конкурентное устаревшее
изменение отклоняется, а приложение переводит его в 409 или предлагает повтор.

## От модели к решению

### Контекст и SQL

Новый объект до persist не связан с контекстом. Managed-объект отслеживается: изменение поля может привести к UPDATE без отдельного save. Detached-объект уже не отслеживается; merge копирует его состояние в managed-экземпляр и возвращает этот экземпляр.

Flush отправляет SQL, но не гарантирует успешный commit. Ошибка ограничения может проявиться при flush или завершении транзакции. При IDENTITY вставка иногда требуется раньше, чтобы получить id. Поэтому важен фактический SQL.

### Связи и загрузка

В двунаправленной связи согласуют обе стороны объектной модели. Owning side управляет внешним ключом. Cascade определяет перенос операций, а не загрузку. Orphan removal может удалить строку при удалении дочернего объекта из связи.

N+1 — запрос списка и дополнительные запросы для каждого элемента. Eager не гарантирует один SQL. `fetch` join, entity graph или проекция выбираются под сценарий. `fetch` join коллекции с пагинацией может размножить строки и потребовать другого плана.

LazyInitializationException характерен для Hibernate; это не универсальный тип ошибки JPA. Сохранение сессии до сериализации может скрыть N+1 вместо исправления загрузки.

### Граница изменения

В стандартном proxy-режиме вызов Transactional-метода должен пройти через proxy. Внутренний вызов обычно обходит механизм. По умолчанию rollback вызывают RuntimeException и Error, для checked-исключений задают подходящие правила, например rollbackFor.

Version отклоняет устаревшее изменение. Это не повод безусловно повторять операцию с прежними данными: API может вернуть 409, UI — предложить перечитать состояние.

Пример возвращает entity как внутренний учебный минимум. Для внешнего API сервис формирует DTO внутри нужной границы загрузки. `ddl-auto=validate` проверяет отображение, но не заменяет миграции и полный аудит ограничений.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 20](../examples/lecture-20-spring-data-jpa/README.md).

```java
@jakarta.persistence.Entity
class ProductEntity {
    @jakarta.persistence.Id
    @jakarta.persistence.GeneratedValue(strategy = jakarta.persistence.GenerationType.IDENTITY)
    private Long id;

    @jakarta.persistence.Column(nullable = false)
    private String name;

    protected ProductEntity() {}
    ProductEntity(String name) { this.name = name; }
}

interface ProductRepository extends org.springframework.data.jpa.repository.JpaRepository<ProductEntity, Long> {}

@org.springframework.stereotype.Service
class ProductService {
    private final ProductRepository repository;

    ProductService(ProductRepository repository) {
        this.repository = repository;
    }

    @org.springframework.transaction.annotation.Transactional
    public ProductEntity create(String name) {
        return repository.save(new ProductEntity(name));
    }
}
```

## Разбор и проверка результата

### Транзакция видна через результат

Создание товара должно оставить строку после успешного завершения сервисного метода. Если сразу после него выброшено исключение, но уже за пределами транзакционной границы, прежний commit автоматически не отменится. Поэтому граница должна включать весь use case, который требуется выполнять атомарно.

Для заказа с позициями проверяется и успешный путь, и ошибка второй позиции. После отказа независимое чтение не должно находить ни заголовок, ни первую позицию. Проверка только исключения не доказывает откат: ошибка могла возникнуть после частичной фиксации.

При двух редакторах версии 5 первый сохраняет изменение и получает версию 6. Второй не должен молча перезаписать результат, отправив старую версию 5. Оптимистическая блокировка делает конфликт наблюдаемым, а интерфейс должен предложить разумное продолжение: перечитать, сравнить изменения или повторить действие по осознанному правилу.

## Типичные ошибки

- entity напрямую уходит в JSON;
- `FetchType.EAGER` на всех связях;
- repository вызывается из View/Controller без сервисной транзакции;
- `ddl-auto=update` в production;
- `equals/hashCode` entity зависит от изменяемых связей.
