# Лекция 21. Безопасность конфигурация и наблюдаемость Spring Boot

Версия для чтения. Основа: [рекомендации к лекции 21](lecture-21.md).

**Цель:** Защитить API и получить диагностические данные без утечки секретов.

## Основные понятия

Аутентификация отвечает «кто пользователь», авторизация — «разрешено ли действие».
Spring Security строит filter chain до контроллера. Правила URI защищают границу
HTTP, method security может дополнительно защищать сервис. Права проверяются на
сервере; скрытая кнопка UI не является защитой. По умолчанию `SecurityContextHolder` хранит контекст в `ThreadLocal`; стратегию
можно заменить, но в типовых servlet-приложениях используется именно она. Для односторонней
передачи контекста на время операции современный JDK предлагает `ScopedValue`
(см. лекцию 14); в типовых Spring-приложениях пока чаще встречается именно
`SecurityContextHolder`.

Пароль никогда не хранится открыто и не шифруется обратимо. `PasswordEncoder`
создаёт salted adaptive hash; параметр стоимости позволяет со временем усиливать
защиту. Токены, session id и ключи не логируют. Для API 401 обычно указывает на необходимость аутентификации, а 403 — на отказ в доступе; поведение зависит также от механизма входа и CSRF.

CSRF использует автоматическую отправку browser credentials для нежелательного
запроса. Для session/cookie browser-приложения защита нужна; решение для stateless
API зависит от реального способа передачи credentials. CORS разрешает браузеру
читать междоменные ответы и настраивается узко по origin, method и header.

Externalized configuration отделяет артефакт от среды. Секреты передаются через
secret store или окружение, но переменные окружения также доступны процессам и
диагностике, поэтому обращение с ними должно быть осторожным.

Actuator health показывает жизнеспособность и готовность, metrics — численные
ряды, logs — события, traces — путь запроса. Label с user id создаёт
неограниченную cardinality и перегружает систему метрик. Correlation id связывает
строки одного запроса, но не должен быть доверенным идентификатором безопасности.

## От модели к решению

### Идентичность и разрешение

Аутентификация устанавливает субъект, авторизация проверяет операцию и объект. Роли USER недостаточно, чтобы разрешить чтение любого заказа по id. Проверка владельца нужна на уровне предметного действия.

Для API отсутствие подходящих credentials обычно даёт 401, недостаток прав — 403. Form-login может перенаправить на вход. Отказ CSRF способен дать 403 ещё до бизнес-операции, поэтому статус читают в контексте цепочки фильтров.

### Пароли и клиент

PasswordEncoder создаёт проверяемое представление пароля с солью и вычислительной стоимостью. HTTP Basic передаёт credentials в Base64; это кодировка, а не шифрование, поэтому нужен HTTPS. Пользователи и encoder настраиваются отдельно от правил доступа.

Stateless сам по себе не исключает CSRF, если браузер автоматически прикладывает credentials. Для cookie-сессии обычно сохраняют CSRF-защиту. CORS её не заменяет.

### Конфигурация примера

Исходный минимум требует аутентификации, но не проверяет роли. Ниже добавлено правило ADMIN для DELETE. Оно показывает роль на уровне HTTP, но не заменяет предметные проверки и остальные правила практики. Bean-метод размещается в конфигурационном классе; нужны зависимости, пользователи и PasswordEncoder.

Метрика заказов увеличивается после успешного результата. Метки описывают ограниченные категории, например канал web/api. Id заказа или email создают огромное число временных рядов. Correlation id связывает журналы, но не доказывает личность клиента; входное значение ограничивают по длине и символам.

Liveness не следует связывать с временной недоступностью БД. Readiness может учитывать БД, если без неё приложение не готово обслуживать запросы.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 21](../examples/lecture-21-spring-security-observability/README.md).

Метод размещается внутри класса с `@Configuration`. Пользователи и `PasswordEncoder` настраиваются отдельно. CSRF остаётся включённым.

```java
@org.springframework.context.annotation.Bean
org.springframework.security.web.SecurityFilterChain security(
    org.springframework.security.config.annotation.web.builders.HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health").permitAll()
            .requestMatchers(org.springframework.http.HttpMethod.DELETE, "/api/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .httpBasic(org.springframework.security.config.Customizer.withDefaults())
        .build();
}
```

## Разбор и проверка результата

### Как читать ответы защищённого API

Для GET к защищённому ресурсу без credentials ожидается 401 при выбранном HTTP Basic. Для DELETE с аутентифицированным USER правило ADMIN не выполнено — ожидается 403. Для ADMIN успешный проход Security означает только допуск к следующему слою: ресурс всё ещё может отсутствовать или операция может нарушать предметное правило.

При проверке изменяющих запросов учитывают включённую CSRF-защиту. Иначе 403 может возникнуть из-за отсутствия CSRF-токена, а тест ошибочно сочтёт это доказательством правильного правила ролей. Тест авторизации должен обеспечить остальные необходимые предпосылки запроса.

Открытый health возвращает минимальный итог без строки подключения, имён пользователей и подробностей исключений. Доступность endpoint и объём публикуемых деталей настраиваются отдельно. Метрики и подробные диагностические endpoint не становятся автоматически публичными только потому, что health разрешён.

## Типичные ошибки

- пароли в plain text;
- `csrf.disable()` без модели клиента;
- `permitAll()` на широком шаблоне;
- секрет в Git или stack trace;
- метрика с email/user id как label.

## Самостоятельная работа

Закрыть API авторизацией по ролям, оставить доступным health endpoint и добавить метрику числа созданных заказов.

**Рекомендации к решению.** Не отключать CSRF механически: сначала определить тип клиента и способ хранения учетных данных. Секреты передавать через окружение.

**Критерии приёмки.** Тесты различают 401 и 403; пароли не хранятся открыто; health не раскрывает чувствительные сведения; метрика имеет ограниченный набор label values.
