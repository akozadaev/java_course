# Лекция 17. Основы веб-приложений: HTTP, REST и безопасность

Версия для чтения. Основа: [рекомендации к лекции 17](lecture-17.md).

## Введение

До этого момента мы работали с локальными данными и прямыми вызовами методов. Однако современные приложения редко существуют изолированно. Они общаются друг с другом через сеть, предоставляя интерфейсы (API) для клиентов: браузеров, мобильных приложений или других серверов.

Стандартом де-факто для такого взаимодействия является протокол **HTTP** и архитектурный стиль **REST**. В этой лекции мы разберем, как устроены HTTP-запросы и ответы, как правильно проектировать API до использования тяжелых фреймворков (вроде Spring) и какие базовые угрозы безопасности нужно учитывать при работе с вебом.

**Цель занятия:** Научиться проектировать корректные HTTP API, понимать семантику методов и кодов состояния, а также реализовывать простые веб-серверы на стандартных средствах Java.

## 1. Протокол HTTP: Запрос и Ответ

HTTP (HyperText Transfer Protocol) — это протокол уровня приложений, работающий по модели «запрос–ответ». Клиент отправляет запрос, сервер обрабатывает его и возвращает ответ.

### Структура HTTP-запроса

Запрос состоит из четырех основных частей:

1.  **Метод (Method)**: Глагол, указывающий на действие, которое нужно выполнить с ресурсом.
2.  **URI (Uniform Resource Identifier)**: Адрес ресурса, с которым производится операция (например, `/users/123`).
3.  **Заголовки (Headers)**: Метаданные запроса (тип контента, авторизация, кэширование и т.д.).
4.  **Тело (Body)**: Данные, передаваемые серверу (используется не во всех методах, обычно не используется в GET; тело GET не имеет общепринятой семантики и может быть отклонено).

Пример текстового представления HTTP/1.1-запроса (после пустой строки показано тело из 32 байт UTF-8; HTTP/2 и HTTP/3 используют другое представление сообщений):
```http
POST /orders HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 32

{"productId": 42, "quantity": 1}
```

### Структура HTTP-ответа

Ответ также имеет четкую структуру:

1.  **Код состояния (Status Code)**: Число, указывающее результат операции (200, 404, 500 и т.д.).
2.  **Заголовки (Headers)**: Метаданные ответа (тип контента, длина, куки).
3.  **Тело (Body)**: Возвращаемые данные (JSON, HTML, бинарные данные) или сообщение об ошибке.

> **Важно:** HTTPS — это тот же HTTP, но обернутый в шифрованный TLS-туннель. HTTPS защищает данные от перехвата при передаче, но **не защищает** от ошибок в логике приложения (например, от отсутствия проверки прав доступа).

## 2. Семантика HTTP-методов

Выбор правильного метода критически важен для понимания того, что делает запрос.

| Метод | Назначение | Идемпотентность* | Безопасность** |
| :--- | :--- | :--- | :--- |
| **GET** | Получение ресурса | Да | Да |
| **POST** | Обработка данных, создание или запуск операции | Не гарантируется | Нет |
| **PUT** | Полная замена ресурса по известному URI | Да | Нет |
| **PATCH** | Частичное обновление ресурса | Не гарантируется | Нет |
| **DELETE** | Удаление ресурса | Да | Нет |

*\*Идемпотентность:* Свойство операции, при котором повтор одинакового запроса имеет тот же предполагаемый эффект на состояние ресурса, что и однократный вызов. Статус и тело ответа могут различаться: первый DELETE вернёт 204, повторный — 404, а ресурс в обоих случаях отсутствует. Это важно для механизмов повторных попыток (retry) при сетевых сбоях. Если вы отправили `DELETE /order/1` и потеряли ответ, безопаснее отправить запрос снова, чем рисковать созданием дубликатов (как могло бы быть с POST).

*\*\*Безопасность (Safe):* Клиент не запрашивает изменение бизнес-состояния. Логирование и другие служебные побочные эффекты допустимы. Safe не означает безопасность передачи данных или право доступа. HEAD также является safe-методом и возвращает заголовки без тела ответа.

## 3. Коды состояния (Status Codes)

Коды состояния группируются по первой цифре:

*   **2xx (Success)**: Запрос успешно обработан.
    *   `200 OK`: Стандартный успех.
    *   `201 Created`: Ресурс успешно создан (часто используется с POST).
    *   `204 No Content`: Успех, но тело ответа пустое (часто для DELETE).
*   **3xx (Redirection)**: Класс перенаправлений и связанных механизмов. Например, 304 Not Modified позволяет использовать кэшированное представление без нового тела; это не переход на другой URL.
*   **4xx (Client Error)**: Запрос не может быть удовлетворён по условиям, отражённым статусом: это не всегда синтаксически неверный запрос.
    *   `400 Bad Request`: Неверный синтаксис или валидация данных.
    *   `401 Unauthorized`: Нет подходящих credentials. Ответ сопровождается WWW-Authenticate с поддерживаемой схемой аутентификации.
    *   `403 Forbidden`: Сервер отказывает в выполнении. Часто пользователь аутентифицирован, но не имеет прав; однако 403 не доказывает факт успешной аутентификации.
    *   `404 Not Found`: Ресурс по указанному URI не найден.
    *   `409 Conflict`: Конфликт с текущим состоянием ресурса (например, попытка создать пользователя с уже занятым email).
    *   `405 Method Not Allowed`: Метод не поддерживается для данного URI (должен сопровождаться заголовком `Allow`).
*   **5xx (Server Error)**: Сервер не смог выполнить запрос. Причиной может быть ошибка обработки или временная недоступность зависимости.
    *   `500 Internal Server Error`: Общая ошибка сервера.

> **Антипаттерн:** Не маскируйте ошибку HTTP-операции статусом `200 OK`. Используйте подходящий статус и понятное машинно-читаемое описание ошибки в теле, если тело разрешено для этого ответа. Инструменты мониторинга, балансировщики нагрузки и клиенты ориентируются именно на коды статусов.

## 4. REST и проектирование ресурсов

REST (Representational State Transfer) — архитектурный стиль распределённых систем с ограничениями client–server, stateless, cache, uniform interface и layered system; code-on-demand необязателен. Stateless означает, что запрос несёт контекст, необходимый для его понимания, а не отсутствие данных на сервере. Ресурсный HTTP API с JSON ещё не обязательно соблюдает все ограничения REST, в частности гипермедиа. Здесь рассматривается практический ресурсный дизайн HTTP API.

### Принципы именования URI

1.  **Ресурсы обычно называют существительными.** Это соглашение проектирования, а не синтаксическое требование HTTP. Операцию можно моделировать отдельным ресурсом, например POST /orders/42/cancellations.
    *   ✅ Правильно: `GET /orders/42/items` (получить товары заказа №42)
    *   Менее удачное ресурсное имя: `GET /getItemsForOrder?id=42`
2.  **Иерархия.** Вложенные ресурсы отражают связь между объектами.
3.  **Множественное число.** Обычно коллекции называют во множественном числе (`/users`, `/products`).

### Представление данных (Representation)

Клиент и сервер должны договориться о формате данных.
*   **Content-Type**: Заголовок, указывающий формат тела запроса/ответа (например, `application/json`).
*   **Accept**: Заголовок запроса, указывающий, какой формат клиент хочет получить.

Данные, передаваемые через API (DTO — Data Transfer Object), не должны быть прямой копией объектов базы данных. Они должны быть адаптированы под нужды клиента.

Для потенциально больших списков следует предусматривать:
*   **Пагинацию**: Чтобы не загружать миллионы записей одним запросом.
*   **Фильтрацию и сортировку**: Параметры запроса (query params).

## 5. Безопасность и особенности веба

Веб-приложения имеют специфические уязвимости, связанные с тем, как работают браузеры и сети.

### Cookies и CSRF

*   **Cookies**: Маленькие фрагменты данных, которые сервер сохраняет в браузере. Браузер автоматически отправляет подходящие cookies с учётом Domain, Path, Secure, SameSite, режима credentials и своих политик. HttpOnly ограничивает чтение из JavaScript, но не автоматическую отправку.
*   **CSRF (Cross-Site Request Forgery)**: Атака, при которой злоумышленник заставляет браузер жертвы выполнить нежелательный запрос на доверенный сайт (например, перевод денег), используя сохраненные cookies. Если сервер полагается только на автоматически отправленные credentials, он может принять запрос за действие пользователя. Защита включает CSRF-токены, подходящий SameSite и проверку источника по выбранной модели приложения.

### CORS (Cross-Origin Resource Sharing)

CORS расширяет same-origin policy и определяет, разрешено ли браузерному JavaScript читать ответ другого origin. Origin — это схема, хост и порт: два адреса на одном хосте с разными портами тоже могут быть разными origin.

Некоторые межсайтовые запросы отправляются сразу, и при отсутствии разрешения браузер лишь скрывает ответ от JavaScript. Для других сначала выполняется preflight OPTIONS; если он отклонён, основной запрос не отправляется. Поэтому отсутствие Access-Control-Allow-Origin не доказывает, что действие на сервере не произошло. CORS не заменяет CSRF-защиту.
> **Важно:** CORS ограничивает браузерный доступ JavaScript к ответам. Клиенты вне браузера, например curl или скрипт, не обязаны соблюдать эту политику. Поэтому CORS **не заменяет** полноценную авторизацию и валидацию токенов.

### Общие правила безопасности

1.  **Ввод недоверенный.** Любые данные от клиента (headers, body, params) должны валидироваться.
2.  **Логирование.** Никогда не логируйте пароли, токены доступа или персональные данные в открытом виде.

## 6. Практический пример: Встроенный HTTP-сервер в Java

Для понимания основ не обязательно сразу использовать Spring. В JDK есть встроенный легкий HTTP-сервер (`com.sun.net.httpserver.HttpServer`), который позволяет увидеть «изнанку» протокола.

### Пример реализации Health Check

Эндпоинт `/health` используется системами мониторинга для проверки работоспособности сервиса.

В JPMS-проекте нужен `requires jdk.httpserver;`. Следующий класс сохраняется в SimpleServer.java. Контекст HttpServer сопоставляется по префиксу, поэтому обработчик отдельно проверяет точный путь. HEAD возвращает те же основные метаданные, что и GET, без тела.

```java
import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class SimpleServer {
    public static void main(String[] args) throws Exception {
        var server = HttpServer.create(new InetSocketAddress("127.0.0.1", 8080), 0);
        server.createContext("/health", exchange -> {
            try {
                if (!"/health".equals(exchange.getRequestURI().getPath())) {
                    exchange.sendResponseHeaders(404, -1);
                    return;
                }
                String method = exchange.getRequestMethod();
                if (!"GET".equals(method) && !"HEAD".equals(method)) {
                    exchange.getResponseHeaders().set("Allow", "GET, HEAD");
                    exchange.sendResponseHeaders(405, -1);
                    return;
                }
                byte[] body = "{\"status\":\"UP\"}".getBytes(StandardCharsets.UTF_8);
                exchange.getResponseHeaders().set("Content-Type", "application/json");
                exchange.getResponseHeaders().set("Cache-Control", "no-store");
                if ("HEAD".equals(method)) {
                    exchange.getResponseHeaders().set("Content-Length", Integer.toString(body.length));
                    exchange.sendResponseHeaders(200, -1);
                } else {
                    exchange.sendResponseHeaders(200, body.length);
                    try (var out = exchange.getResponseBody()) {
                        out.write(body);
                    }
                }
            } finally {
                exchange.close();
            }
        });
        server.createContext("/", exchange -> {
            try {
                exchange.sendResponseHeaders(404, -1);
            } finally {
                exchange.close();
            }
        });
        Runtime.getRuntime().addShutdownHook(new Thread(() -> server.stop(1)));
        server.start();
        System.out.println("Server started at http://127.0.0.1:8080");
    }
}
```

Запуск из каталога с исходником:

```bash
javac --add-modules jdk.httpserver SimpleServer.java
java --add-modules jdk.httpserver SimpleServer
```

Проверки из другого терминала:

```bash
curl -i http://127.0.0.1:8080/health
curl -I http://127.0.0.1:8080/health
curl -i -X POST http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/health/extra
curl -i http://127.0.0.1:8080/missing
```

Ожидаются соответственно: 200 с JSON `{"status":"UP"}`; 200 без тела; 405 с Allow: GET, HEAD; 404; 404. Порядок и регистр имён заголовков несущественны. Остановка — Ctrl+C.

В sendResponseHeaders положительная длина задаёт точное число байт тела, ноль включает chunked transfer encoding, а минус один означает отсутствие тела. Для HEAD тело не отправляется независимо от содержания представления.

Этот health сообщает только, что обработчик способен ответить. Он не проверяет БД и не доказывает готовность всех зависимостей. Разделение liveness и readiness рассматривается в следующих темах.

## 7. Типичные ошибки при проектировании API

1.  **GET изменяет данные.** Например, `GET /deleteUser/1`. Это ломает кэширование и может привести к случайным удалениям при предзагрузке ссылок браузером.
2.  **Всегда возвращать 200.** Даже если произошла ошибка, возвращать JSON `{ "error": "..." }` со статусом 200. Это лишает клиента возможности стандартными средствами отличить успех от неудачи.
3.  **Отсутствие Content-Type.** Клиент не знает, как парсить ответ (текст это, JSON или XML).
4.  **Глаголы в URI.** `/createOrder`, `/getUser`. В REST используются существительные и методы HTTP.
5.  **Путаница CORS и Авторизации.** Разрешение CORS для всех доменов (`*`) не делает API безопасным, если нет проверки токенов.
