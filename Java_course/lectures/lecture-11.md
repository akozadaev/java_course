# Лекция 11. Дата время локализация и регулярные выражения

Версия для чтения. Основа: [рекомендации к лекции 11](lecture-11.md).

**Цель:** Корректно работать с временными зонами, форматами и пользовательским вводом.

## Основные понятия

Дата, локальное время и момент времени — разные понятия. `LocalDate` хранит дату
без времени, `LocalDateTime` — местные показания часов без зоны, `Instant` —
однозначный момент на временной шкале UTC, `ZonedDateTime` сочетает местные
показания и правила `ZoneId`. Для события в системе обычно хранят `Instant`, а
зону применяют на границе ввода и отображения.

`ZoneId` содержит исторические и будущие правила переходов, тогда как
`ZoneOffset` — только фиксированное смещение. Из-за переходов час может
повториться или отсутствовать. Прибавление `Duration.ofHours(24)` и
`Period.ofDays(1)` к zoned-времени может дать разные локальные показания.

Классы `java.time` неизменяемы и потокобезопасны. `DateTimeFormatter` явно задаёт
формат и Locale. Не следует разбирать пользовательскую дату неявным системным
форматом: результат станет зависеть от машины. Для тестируемого текущего времени
в сервис передают `Clock`.

`Locale` влияет на язык, правила форматирования и сортировки. Текст интерфейса
хранят в `ResourceBundle`, а не смешивают с бизнес-кодом. Денежный формат не
заменяет валюту как часть предметной модели.

Регулярное выражение описывает язык строк. `matches` проверяет всю строку,
`find` ищет фрагмент. Сложные вложенные квантификаторы могут привести к
катастрофическому backtracking; regex не следует использовать как полноценный
парсер сложных форматов. Скомпилированный `Pattern` переиспользуют.

## От модели к решению

### Дата и момент отвечают на разные вопросы

«Когда произошло событие?» обычно требует Instant. «В какой день родился человек?» требует LocalDate. Будущая встреча «по понедельникам в 10:00 по местному времени» задаётся локальными правилами и зоной, а не одним UTC-моментом.

Преобразование Instant в зону однозначно. Обратное преобразование локального времени может попасть в пропуск или повтор при переводе часов. `atZone()` применяет стандартное правило разрешения ситуации; если оно не подходит предметной области, нужна явная политика.

### Интервалы и формат

Duration измеряет время в секундах и наносекундах, Period — календарных годах, месяцах и днях. Календарный день при переходе часов не обязан длиться 24 часа. Прибавление месяца к концу января также требует календарного правила.

Момент `2026-09-17T12:00:00Z` в примере переводится в Europe/Moscow. При выводе трёх зон Instant остаётся тем же; меняется представление. Актуальность правил зависит от базы часовых поясов JDK, поэтому обновление среды важно даже при неизменном исходнике.

В шаблонах DateTimeFormatter MM означает месяц, mm — минуты. `uuuu` задаёт год, а `YYYY` — год недельного календаря: около Нового года результаты могут различаться. Для строгой проверки ввода нужен явный formatter с ResolverStyle.STRICT.

### Управляемые зависимости

Clock.fixed закрепляет текущий момент в тесте. Прямые вызовы Instant.now внутри сервиса могут попасть на границу суток или срока действия. Переданный Clock делает зависимость явной.

Regex в Java проходит два разбора: строкового литерала и регулярного выражения. Класс цифр в исходнике записывается как `"\\d+"`. `matches()` проверяет всю строку, find ищет очередное совпадение. `Pattern` можно использовать совместно, а `Matcher` хранит изменяемое состояние отдельного поиска.

## Практический пример

Пример сохраняется в `TimeDemo.java` и запускается командами `javac TimeDemo.java` и `java TimeDemo`. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 11](../examples/lecture-11-date-time-regex/README.md).

```java
import java.time.*;
import java.time.format.DateTimeFormatter;

public class TimeDemo {
    public static void main(String[] args) throws Exception {
        var instant = Instant.parse("2026-09-17T12:00:00Z");
        var tambov = instant.atZone(ZoneId.of("Europe/Moscow"));
        System.out.println(tambov.format(DateTimeFormatter.ISO_ZONED_DATE_TIME));
    }
}
```

## Разбор и проверка результата

### Одно событие в разных представлениях

Для Europe/Moscow пример выводит местные показания 15:00 того же дня при UTC-моменте 12:00. В ISO-представлении видны и смещение, и идентификатор зоны. При выборе другой зоны меняется отображение, а не само событие.

LocalDateTime без зоны не позволяет восстановить единственный Instant. Сохранённая строка «2026-09-17 15:00» не говорит, идёт ли речь о Москве, другом городе или серверной зоне. Это особенно опасно при обмене данными между системами.

Locale определяет языковые и региональные правила форматирования, но не заменяет ZoneId. Русский язык интерфейса сам по себе не означает московскую зону. Поэтому зона, язык и валюта задаются как отдельные параметры, даже если у части пользователей их значения обычно совпадают.

## Типичные ошибки

- хранение серверного времени как `LocalDateTime` без зоны;
- фиксированное `+03:00` вместо `Europe/Moscow` для общего случая;
- `LocalDateTime.now()` внутри тестируемой логики;
- неявный Locale;
- regex для вложенного JSON или HTML.

## Самостоятельная работа

Составить расписание события в UTC и вывести локальное время для трех часовых поясов.

**Рекомендации к решению.** Хранить момент события как Instant. Часовой пояс применять при вводе и отображении, а не заменять фиксированным смещением.

**Критерии приёмки.** Переходы часовых поясов учитывает ZoneId; формат явно задан; некорректный ввод не приводит к необработанному исключению.
