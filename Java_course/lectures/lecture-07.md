# Лекция 7. Наследование интерфейсы и композиция

Версия для чтения. Основа: [рекомендации к лекции 7](lecture-07.md).

**Цель:** Использовать полиморфизм и выбирать композицию вместо лишнего наследования.

## Основные понятия

Наследование выражает отношение «является», интерфейс — контракт поведения,
композиция — отношение «использует». Подтип обязан быть пригоден везде, где
ожидается базовый тип. Если наследник усиливает предусловия или ломает ожидания,
полиморфизм становится источником дефектов.

Интерфейс задаёт операции без привязки к хранению состояния. Класс может
реализовать несколько интерфейсов. Абстрактный класс способен хранить общее
состояние и частичную реализацию, но связывает наследников одной иерархией.
`@Override` просит компилятор проверить, что метод действительно переопределён.

Default-методы помогают эволюционировать интерфейс, но не должны превращать его
в склад несвязанных утилит. Static-метод интерфейса вызывается через имя
интерфейса и не является полиморфным.

Sealed-иерархия ограничивает допустимые реализации. Компилятор способен проверить
полноту pattern matching по закрытому набору вариантов. Открытый интерфейс лучше
подходит для расширяемой стратегии, где новые реализации добавляют клиенты.

Композиция обычно гибче: `DeliveryService` получает `DeliveryPolicy` через
конструктор и делегирует расчёт. Сервис легко тестировать и менять независимо от
стратегии. Это практическое применение dependency inversion, а не требование
создавать интерфейс для каждого класса.

SOLID полезен как набор вопросов: есть ли у класса одна причина изменения,
добавляется ли вариант без переписывания стабильного кода, сохраняют ли подтипы
контракт, не заставляет ли интерфейс зависеть от лишних методов, направлены ли
зависимости к абстракциям.

## От модели к решению

### Полиморфизм на примере доставки

Сервис должен знать операцию расчёта доставки, но не каждый конкретный класс политики. Курьерская доставка и самовывоз реализуют один интерфейс. Добавление политики не требует цепочки instanceof внутри сервиса: нужный объект передаётся при создании.

Выбор реализации всё равно может происходить на границе приложения: конфигурация или обработчик пользовательского выбора сопоставляет код доставки объекту. Важно, чтобы алгоритм расчёта не повторял этот выбор во всех местах.

### Подстановка и композиция

Контракт включает больше, чем сигнатуру. Если интерфейс разрешает нулевую стоимость заказа, реализация не должна неожиданно отклонять её. Если метод обещает не менять заказ, подтип не может менять позиции. Такие нарушения ломают подстановку даже при успешной компиляции.

Наследование полезно при устойчивом отношении подтипов и сознательно спроектированных точках расширения. Композиция позволяет независимо варьировать хранение, расчёт и уведомление, заменяя используемые объекты.

### Закрытые варианты

Shape разрешает только Circle и Rectangle. Record является final, поэтому эти ветви не имеют наследников. Прямой наследник sealed-типа должен быть final, sealed или non-sealed. Правила размещения зависят от наличия именованного модуля.

Метод area вызывается полиморфно. Формулы требуют допустимых размеров: отрицательные значения, NaN и бесконечность не должны становиться корректными геометрическими данными. В примере конструкторы проверяют вход. Вычисление площади в double всё равно имеет ограничение точности и может переполниться для очень больших размеров.

SOLID не требует интерфейса для каждого класса. Абстракция полезна там, где есть самостоятельный контракт или реальная граница замены. Чрезмерное дробление простого вычисления способно ухудшить чтение.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 7](../examples/lecture-07-polymorphism-composition/README.md).

```java
sealed interface Shape permits Circle, Rectangle {
    double area();
}
record Circle(double radius) implements Shape {
    Circle {
        if (!Double.isFinite(radius) || radius < 0) throw new IllegalArgumentException("radius");
    }
    public double area() { return Math.PI * radius * radius; }
}
record Rectangle(double width, double height) implements Shape {
    Rectangle {
        if (!Double.isFinite(width) || !Double.isFinite(height) || width < 0 || height < 0) {
            throw new IllegalArgumentException("width or height");
        }
    }
    public double area() { return width * height; }
}
```

## Разбор и проверка результата

### Один вызов для разных фигур

Переменная типа Shape может ссылаться на Circle или Rectangle. Вызов area выбирает реализацию по фактическому объекту: круг радиуса 2 даёт примерно 12,57, прямоугольник 3 на 4 — 12. Вызывающий код работает с одним контрактом, а не извлекает размеры через проверки типов.

Интерфейс определяет доступные операции, но не даёт создать объект сам по себе. Для создания нужен конкретный класс, фабрика или внешний выбор реализации. Поэтому полиморфизм не устраняет знание конкретных типов из всей программы — он ограничивает его местом создания.

Default-метод имеет реализацию, которую класс может переопределить. Если два интерфейса дают несовместимые default-методы одной сигнатуры, класс должен разрешить конфликт явно. Это показывает, почему множественная реализация интерфейсов не равна бесконтрольному наследованию любого поведения.

## Типичные ошибки

- наследование только ради повторного использования пары методов;
- base-класс с `protected` изменяемыми полями;
- `instanceof`-цепочка вместо вызова полиморфного метода;
- интерфейс из десятков несвязанных операций;
- зависимость сервиса от конкретной стратегии, созданной через `new` внутри.

## Самостоятельная работа

Реализовать несколько способов доставки через интерфейс DeliveryPolicy и сервис расчета без instanceof.

**Рекомендации к решению.** Зависимость передать в конструктор сервиса. Новая стратегия должна добавляться отдельным классом без изменения сервиса.

**Критерии приёмки.** Полиморфизм заменяет цепочку условий по типу; нет публичных изменяемых полей; поведение каждой стратегии проверено.
