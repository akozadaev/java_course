# Лекция 9. Обобщения коллекции и контракты equals hashCode

Версия для чтения. Основа: [рекомендации к лекции 9](lecture-09.md).

**Цель:** Выбирать коллекцию по операциям и писать типобезопасный API.

## Основные понятия

Коллекцию выбирают по требуемым операциям, а переменную объявляют через
интерфейс. `List` сохраняет порядок и допускает повторы, `Set` обеспечивает
уникальность, `Queue` моделирует очередь, `Map` связывает ключ со значением.
`ArrayList` даёт быстрый доступ по индексу, но вставка в середину сдвигает
элементы. `HashMap` и `HashSet` дают ожидаемое O(1) для основных операций при
хорошем хэшировании; `TreeMap` поддерживает порядок за O(log n).

Контракт `equals` требует рефлексивности, симметричности, транзитивности,
согласованности и ложного результата для `null`. Равные объекты обязаны иметь
одинаковый `hashCode`. Изменение поля, участвующего в равенстве ключа `HashMap`,
после вставки делает элемент практически недоступным. Поэтому ключи удобно
делать неизменяемыми.

Generics обеспечивают типобезопасность без ручных cast. `List<String>` не является подтипом `List<Object>`: параметры обобщённых типов инвариантны. Wildcard `? extends T` удобен
для источника значений, `? super T` — для получателя: правило PECS означает
Producer Extends, Consumer Super. Из producer нельзя безопасно добавлять
значения, кроме `null`.

Type erasure означает, что большинство параметров типа отсутствует в runtime.
Нельзя создать `new T()`, массив `new T[]` или в общем случае проверить объект типа Object через `instanceof List<String>`.
Raw-типы отключают проверку компилятора и оставлены только для совместимости.

Фабрики `List.of`, `Set.of`, `Map.of` создают неизменяемые коллекции и не
принимают `null`. `List.copyOf` создаёт неизменяемый снимок, но не копирует сами
изменяемые элементы глубоко.

## От модели к решению

### Выбор структуры по операции

Для оценок важен порядок и допустимы повторы — подходит List. Для уникальных дисциплин подходит Set, но HashSet не обещает порядок обхода. Для порядка вставки есть LinkedHashSet, для сортировки — TreeSet. Индекс студентов по группе имеет тип `Map<String, List<Student>>`.

Map не является подтипом Collection. Представления keySet, values и entrySet позволяют обходить ключи, значения и пары. Если значение null допустимо, одного get недостаточно для различения отсутствующего ключа и сохранённого null. Проще запретить null по контракту либо использовать containsKey.

### Устойчивость ключа

HashMap выбирает область поиска по хэшу, затем сравнивает ключи через equals. Если после вставки изменить поле, определяющее хэш, поиск может не найти прежнюю запись. Она при этом физически остаётся в карте. Record с неизменяемыми компонентами помогает избежать такого дефекта.

Неравные объекты могут иметь одинаковый hashCode: коллизия допустима. Равные объекты с разными хэшами нарушают контракт. TreeMap опирается на сравнение; несогласованность компаратора с equals тоже может дать неожиданное понимание уникальности.

### Границы обобщений

Из `List<? extends Number>` можно читать Number, но нельзя добавить произвольный Integer: фактически это может быть список Double. В `List<? super Integer>` можно добавлять Integer, но читать безопасно только Object. PECS описывает роли параметров, а не запрещает любое изменение: clear не зависит от конкретного типа элемента.

В frequencies метод merge накапливает число вхождений. Map.copyOf запрещает менять структуру результата; порядок обхода не обещан. Контракт запрещает null как сам список и его элементы. Явная проверка полезнее позднего сбоя: HashMap приняла бы ключ null, а Map.copyOf его отклонила бы. Ключи результата должны сохранять устойчивое равенство всё время использования.

## Практический пример

Пример сохраняется в `FrequencyDemo.java` и запускается командами `javac FrequencyDemo.java` и `java FrequencyDemo`. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 9](../examples/lecture-09-generics-collections/README.md).

```java
import java.util.*;

public class FrequencyDemo {
    static <T> Map<T, Long> frequencies(List<T> values) {
        Objects.requireNonNull(values, "values");
        var result = new HashMap<T, Long>();
        for (var value : values) {
            result.merge(Objects.requireNonNull(value, "element"), 1L, Long::sum);
        }
        return Map.copyOf(result);
    }

    public static void main(String[] args) throws Exception {
        System.out.println(frequencies(List.of("Java", "SQL", "Java")));
    }
}
```

## Разбор и проверка результата

### Что получится в карте частот

Для списка `Java, SQL, Java` результат содержит пары Java → 2 и SQL → 1. Порядок печати этих пар не является частью контракта. Тест сравнивает карты по содержимому, а не строку их случайного представления.

Обобщённый параметр T позволяет считать и строки, и другие подходящие ключи одним алгоритмом. Это не означает, что любое поведение equals автоматически разумно: массивы, например, по умолчанию сравниваются по идентичности, а не содержимому элементов.

Копирование карты защищает её структуру, но не делает глубокую копию ключей. Если ключ изменяем, проблема поиска возможна и в возвращённой неизменяемой карте. Поэтому неизменяемая коллекция и неизменяемые элементы — разные свойства, которые проверяют отдельно.

## Типичные ошибки

- выбор `List` для постоянного поиска уникальности;
- нарушение пары `equals`/`hashCode`;
- изменяемый ключ `HashMap`;
- raw `List` и cast во время чтения;
- предположение, что `HashMap` сохраняет порядок.

**Рекомендации к решению.** Для каждого требования записать ключевую операцию: поиск, порядок, уникальность или очередь. После этого выбрать интерфейс коллекции.

**Критерии приёмки.** Тест воспроизводит проблему изменяемого ключа и подтверждает исправление; выбор коллекции объяснен; ключи Map неизменяемы и имеют согласованные equals и hashCode; наружу не возвращается изменяемое внутреннее состояние; для `frequencies` зафиксирована и проверена политика относительно `null` во входном списке.
