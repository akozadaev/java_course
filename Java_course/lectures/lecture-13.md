# Лекция 13. Модули рефлексия аннотации и устройство JVM

Версия для чтения. Основа: [рекомендации к лекции 13](lecture-13.md).

**Цель:** Понимать границы модулей, метаданные классов и базовую модель выполнения JVM.

## Основные понятия

JPMS группирует пакеты в именованные модули. `requires` объявляет зависимость,
`exports` открывает публичный пакет другим модулям. Публичный класс во внутреннем
неэкспортированном пакете остаётся недоступным клиенту модуля. Classpath и module
path — разные режимы разрешения зависимостей; миграция библиотек требует
понимания automatic modules.

Reflection позволяет исследовать классы, методы, поля и аннотации в runtime.
Она используется контейнерами и сериализаторами, но ослабляет статические
гарантии, может нарушать инкапсуляцию и усложняет native image. Аннотация сама по
себе ничего не выполняет: её должен прочитать компилятор, annotation processor
или runtime-код. Важны `Retention` и `Target`.

Class loader загружает байткод и связывает символические ссылки. Идентичность
класса включает его имя и загрузчик. JVM сначала интерпретирует или компилирует
код, а JIT оптимизирует горячие участки на основании профиля выполнения.
Поэтому микробенчмарки без прогрева часто измеряют не то, что задумано.

Стек каждого потока хранит кадры вызовов и локальные значения; heap содержит
объекты, доступные разным потокам. Garbage collector освобождает недостижимые
объекты, но не закрывает файлы и соединения вовремя. Утечка памяти в Java — это
сохранение ненужной достижимости.

`jcmd` показывает процессы и команды JVM, `jstack` — снимки потоков, JFR —
низконакладный профиль событий. Диагностику начинают с измерения, а не с
случайной смены параметров GC.

## От модели к решению

### Пакет и модуль

Публичный класс доступен клиенту именованного модуля только при экспорте пакета и наличии читаемости модуля. `exports` не открывает private-поля для глубокой рефлексии: для этого служит opens, при необходимости адресованный конкретному модулю.

В примере экспортируется только edu.example.catalog.api. Реализацию можно оставить в edu.example.catalog.internal. Проверка недоступности выполняется из отдельного клиентского модуля: внутри того же модуля обращаться к внутреннему пакету допустимо. Зависимость от java.sql объявляется через requires, а java.base читается автоматически.

### Метаданные и выполнение

Аннотация сама ничего не запускает. `@Retention(RUNTIME)` сохраняет метаданные для reflection, CLASS — в class-файле без обязательной доступности через reflection, SOURCE — только на этапе исходника. `@Target` ограничивает места применения. Обработчик или контейнер должен прочитать метаданные и выполнить действие.

Reflection переносит часть ошибок на выполнение. Переименование метода, указанного строкой, может пройти компиляцию и затем дать NoSuchMethodException. `setAccessible` не является универсальным обходом модульной инкапсуляции: доступ может быть запрещён.

### JVM и диагностика

Одинаковое полное имя класса не гарантирует одинаковую runtime-идентичность: важен определивший его загрузчик. Это проявляется в контейнерах и системах плагинов с независимыми копиями библиотек.

Разделение стека и heap — полезная модель, а не обещание физического размещения каждого объекта после JIT-оптимизации. GC освобождает недостижимые объекты, но статический кэш может сохранять ненужную достижимость большого графа.

Снимок потоков помогает искать ожидания и взаимные блокировки; JFR связывает события во времени. Измерять нужно характерный сценарий. Короткий цикл без прогрева и защиты от оптимизаций не заменяет корректный микробенчмарк.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 13](../examples/lecture-13-modules-reflection-jvm/README.md).

```java
// module-info.java
module university.catalog {
    exports edu.example.catalog.api;
}

// edu/example/catalog/api/Main.java — отдельный файл
package edu.example.catalog.api;

public class Main {
    public static void main(String[] args) {
        System.out.println("Module API");
    }
}

// Запуск модульного приложения из каталога с module-info.java:
// javac -d out module-info.java edu/example/catalog/api/Main.java
// java --module-path out -m university.catalog/edu.example.catalog.api.Main
```

## Разбор и проверка результата

### Проверка модульной границы

После компиляции module-info.class находится в корне out, а Main.class — в подкаталогах пакета. Команда с `--module-path out` находит модуль university.catalog и запускает его главный класс. В примере несколько файлов показаны в одном блоке; разделять их нужно по указанным комментариям, поскольку package не может идти после объявления module в одном файле.

Чтобы проверить инкапсуляцию, создают клиентский модуль с requires university.catalog. Он может импортировать публичный класс из экспортированного api-пакета, но импорт класса из internal-пакета должен завершиться ошибкой компиляции. Это и есть наблюдаемая проверка границы.

Без отдельного клиента успешный запуск Main подтверждает только работоспособность приложения. Он не доказывает, что внутренний API скрыт от других модулей. Проверка свойства должна соответствовать самому свойству, а не ближайшему удобному запуску.

## Типичные ошибки

- `exports` всех пакетов;
- смешение classpath и module path;
- ожидание поведения только от наличия аннотации;
- вызов private-членов рефлексией без необходимости;
- использование `System.gc()` как исправления утечки.

## Самостоятельная работа

Разделить небольшое приложение на API и реализацию, экспортировать только API-пакет.

**Рекомендации к решению.** Не открывать все пакеты без причины. Зафиксировать, какая зависимость требует рефлексивного доступа.

**Критерии приёмки.** Клиент видит публичный API и не компилируется при обращении к внутреннему пакету; модуль запускается заявленной командой.
