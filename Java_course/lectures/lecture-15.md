# Лекция 15. Тестирование Java кода

Версия для чтения. Основа: [рекомендации к лекции 15](lecture-15.md).

**Цель:** Писать быстрые воспроизводимые тесты и отделять модульные проверки от интеграционных.

## Основные понятия

Тест фиксирует наблюдаемое поведение и позволяет безопасно менять реализацию.
Хороший модульный тест быстрый, изолированный, воспроизводимый и сообщает причину
сбоя. Структура Arrange–Act–Assert отделяет подготовку, действие и проверку, а имя
описывает условие и ожидаемый результат.

JUnit Jupiter обнаруживает методы с `@Test`; lifecycle по умолчанию создаёт новый
экземпляр класса на каждый тест. `@BeforeEach` не должен скрывать существенную
часть сценария. Parameterized tests полезны для таблиц границ, но не следует
объединять в них совершенно разные поведения.

Test double заменяет зависимость. Stub возвращает подготовленные данные, mock
проверяет взаимодействия, fake содержит упрощённую рабочую реализацию. Mockito
уместен на границе сервиса, но мокирование DTO, коллекций и каждого внутреннего
класса связывает тест с реализацией. Предпочтительнее проверять результат и
состояние, если взаимодействие не является контрактом.

Интеграционный тест проверяет совместную работу компонентов. Testcontainers
запускает настоящую PostgreSQL и обнаруживает различия SQL, типов и транзакций,
которые H2 может скрыть. Контейнер медленнее, поэтому тестовую пирамиду сохраняют:
много модульных и меньше интеграционных тестов.

Время, случайность, файловая система и сеть делают тест нестабильным, если не
управляются. Передавайте `Clock`, генератор идентификаторов и интерфейсы внешних
клиентов. Тест не должен зависеть от порядка, локального часового пояса и данных
предыдущего запуска.

## От модели к решению

### Тестируемое поведение

Проверка `90 → A` фиксирует внешний контракт. Она не должна требовать switch вместо if: оба решения могут быть правильными. Значения 89 и 90 защищают границу, отрицательный балл проверяется отдельным сценарием ожидаемого исключения.

Для заказа нужны обычные данные, пустой набор по выбранному контракту, некорректное количество, округление и отказ зависимости. Набор сценариев выбирается по рискам, а не ради вызова каждой приватной функции.

### Подмена зависимости

Stub возвращает заданный товар для проверки расчёта. Fake хранит данные в памяти и может обслуживать несколько сценариев. Mock полезен, если само взаимодействие является требованием, например уведомление отправляется один раз после успешного действия.

Точная последовательность всех внутренних вызовов обычно хрупка: рефакторинг ломает тест без изменения результата. Но отсутствие внешнего платежа при ошибке валидации может быть важным контрактом. Значение имеет смысл взаимодействия.

### Интеграция и повторяемость

Testcontainers требует Docker-совместимого окружения и образа БД. Отсутствие ручной установки PostgreSQL не означает отсутствия инфраструктурных требований. Версию образа фиксируют, схему создают миграциями, данные сценария готовят явно.

Тест отката читает итоговое состояние через независимое соединение или новую транзакцию после завершения проверяемой операции. Проверка внутри ещё открытого persistence context может скрыть реальный результат commit или rollback.

Surefire обычно выполняет модульные тесты. Failsafe включит интеграционные тесты в verify только при правильной настройке плагина и имён классов. Зелёная команда, не обнаружившая нужные тесты, не подтверждает контракт: важно число выполненных сценариев.

## Практический пример

Ниже приведён учебный фрагмент. Структура проекта, зависимости и команды запуска находятся в [проекте лекции 15](../examples/lecture-15-junit-testing/README.md).

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

class GradeTest {
    @ParameterizedTest
    @CsvSource({"90,A", "89,B", "60,D", "59,F"})
    void mapsScoreToLabel(int score, String expected) {
        assertEquals(expected, Grade.label(score));
    }
}
```

## Разбор и проверка результата

### Почему четыре строки дают четыре проверки

CsvSource задаёт четыре набора входа: 90/A, 89/B, 60/D и 59/F. Каждый вызов тестового метода получает свою пару. AssertEquals сравнивает ожидаемую категорию с фактической и при ошибке показывает различие. Отдельный запуск не требует копировать четыре одинаковых метода.

Для примера нужен Grade из лекции 4 в доступном тесту пакете и зависимость junit-jupiter с поддержкой параметризованных тестов. Одного копирования импортов в обычный main недостаточно: тест обнаруживает и запускает JUnit engine через настроенный инструмент.

Сценарий ошибочного балла удобнее выразить отдельным assertThrows с проверкой типа ошибки. Нельзя считать успешным тестом любое исключение: NullPointerException вместо ожидаемого IllegalArgumentException может указывать на другой дефект. Проверка сообщения уместна, если стабильный текст или код ошибки является частью контракта.

## Типичные ошибки

- тест приватного метода через reflection;
- общий изменяемый fixture между тестами;
- `Thread.sleep` для ожидания асинхронного результата;
- мокирование всего Spring-контекста;
- интеграционный тест, требующий вручную созданной локальной БД.

**Рекомендации к решению.** Тестировать наблюдаемое поведение, а не приватные методы. Для времени и случайности передать управляемые зависимости.

**Критерии приёмки.** Тесты независимы от порядка запуска; не требуют ручной настройки локальной БД; падение сообщает ожидаемое и фактическое значение.
